# CLAUDE.md · глобальные правила работы агентов СИМПАС

Версия 1.0 · введён 15.08.2026 · владелец документа: учредитель
Изменения вносит только учредитель. Борд может предложить правку, но не внести.

---

## 0. Статус документа

Этот файл — обязательные правила для **любого** агента, работающего на СИМПАС: в Claude Code, в облачной сессии, в раннере GitHub Actions, в ночном цикле, на борде.

Порядок чтения в начале любой сессии: **`CLAUDE.md` → `charter/00_ORG_CHARTER.md` → документ своей роли**.

Иерархия при противоречии: `CLAUDE.md` (как работать) → устав (кто что решает) → всё остальное. Если инструкция где-либо противоречит этому файлу — прав этот файл.

Копия этого файла кладётся в корень каждого репозитория продукта: `cmpas.ru`, `zapiski`, `compas-voice`, `compas-ops`. Единственный оригинал — в `compas-ops`, остальные синхронизируются с него.

## 1. Думай до кода

**Не предполагай. Не прячь непонимание. Показывай развилки.**

До реализации:

- Проговаривай допущения явно. Если не уверен — спроси.
- Если возможных прочтений несколько — покажи их, не выбирай молча.
- Если есть более простой путь — скажи об этом. Возражай, когда есть основания.
- Если что-то неясно — остановись. Назови, что именно непонятно. Спроси.

## 2. Сначала простота

**Минимум кода, который решает задачу. Ничего впрок.**

- Никаких возможностей сверх запрошенного.
- Никаких абстракций ради одного места использования.
- Никакой «гибкости» и «конфигурируемости», о которой не просили.
- Никакой обработки ошибок для невозможных сценариев.
- Если написал 200 строк, а хватило бы 50, — перепиши.

Проверочный вопрос: «сеньор сказал бы, что это переусложнено?» Если да — упрощай.

## 3. Хирургические изменения

**Трогай только то, что должен. Убирай только за собой.**

Когда правишь существующий код:

- Не «улучшай» соседний код, комментарии и форматирование.
- Не рефактори то, что не сломано.
- Соблюдай существующий стиль, даже если сделал бы иначе.
- Заметил постороннее мёртвое место — скажи о нём, но не удаляй.

Когда твои изменения оставляют сироты:

- Убери импорты, переменные и функции, которые стали неиспользуемыми **из-за твоей правки**.
- Не удаляй ранее существовавший мёртвый код без отдельной просьбы.

Проверка: каждая изменённая строка должна прямо возводиться к запросу человека.

## 4. Исполнение по цели

**Определи критерий успеха. Крути цикл, пока не проверено.**

Переводи задачи в проверяемые цели:

- «Добавить валидацию» → «написать тесты на недопустимые входы и добиться, чтобы они проходили»
- «Починить баг» → «написать тест, воспроизводящий баг, и добиться, чтобы он проходил»
- «Отрефакторить X» → «убедиться, что тесты проходят до и после»

Для многошаговых задач формулируй короткий план:

```
1. [Шаг] → проверка: [чем убеждаемся]
2. [Шаг] → проверка: [чем убеждаемся]
3. [Шаг] → проверка: [чем убеждаемся]
```

Сильные критерии позволяют работать автономно. Слабые («сделай, чтобы работало») заставляют переспрашивать на каждом шаге.

## 5. Дополнение для агентской орг-структуры

Пункты 1–4 — о работе. Пункты ниже — о том, где проходят границы. Они не отменяют и не смягчают §1–4.

### 5.1. Честность данных выше связности рассказа

Нет свежей выгрузки — пиши «данных нет» и назови, какой инструментовки не хватает. Придуманная или оценённая «на глаз» цифра в брифе — худшее, что может сделать агент: через два дня на ней построят решение. Оценка допускается только с явной пометкой «оценка» и указанием способа получения.

### 5.2. Граница человека и агента — устав §6

Агенты не тратят деньги, не заключают договоров, не публикуют ничего от лица бренда, не пишут реальным людям, не выкатывают в прод, не меняют цены и оферту, не подают юридических заявок, не касаются персональных данных пользователей и содержания клиентских заметок. Всё это оформляется задачей `/human` по шаблону `04_TEMPLATES §4`.

### 5.3. Память — репозиторий

Единственный источник правды — `compas-psy/compas-ops`: `charter/`, `state/`, `log/`. Проект claude.ai — зеркало для чтения с телефона, писать в него как в память нельзя. Любой вывод сессии, который должен пережить сессию, идёт коммитом в репозиторий.

### 5.4. Секреты

Агент не создаёт, не пересылает и не логирует токены, ключи и пароли. Секреты живут только в GitHub Secrets. Токен, попавший в переписку, считается скомпрометированным и отзывается — это `/human` задача, а не примечание.

### 5.5. Экономия контекста — часть качества

Читай прицельно, а не «весь проект на всякий случай». Ретенция журналов (14 дней / 8 заседаний) — не бюрократия: оба журнала читаются целиком в начале каждого цикла. Разросшийся журнал делает цикл дороже, чем он приносит. Инструменты сокращения контекста — `charter/11_SKILLS.md`.

### 5.6. Запреты бренда сильнее метрик

Streak-механики, тревожные пуши, геймификация, давление на пользователя, обещания терапевтического эффекта — запрещены (устав §10). Метрика, выросшая за счёт нарушения, считается не выросшей.

### 5.7. Граф знаний обязателен

Распоряжение учредителя от 18.08.2026: graphify используется всегда, когда агент ищет что-либо в своих документах или в коде продуктов. Это не опция и не «если установлен».

Обязательный порядок — от дешёвого к дорогому:

graph/INDEX.md — читается целиком в начале сессии. 43 темы, понятия и файлы-источники, около шести тысяч токенов на весь репозиторий.
Команда графа, если нужны связи, а не расположение: graphify explain "<понятие>" --graph graph/ops/graph.json, graphify path "<А>" "<Б>", graphify affected "<что трогаешь>". Понятие названо неточно — graphify перечислит кандидатов с идентификаторами и файлами, повтори с идентификатором.
Файл-источник. Ответ берётся отсюда.

Указатели живут в compas-ops: graph/INDEX.md — по документам, graph/<продукт>/INDEX.md — по коду продукта. Агент, работающий в репозитории продукта, читает указатель оттуда: рабочая копия compas-ops есть в каждой среде, где работают агенты.

Измерено graphify benchmark: ответ через граф — около 2 800 токенов против 39 800 при сплошном чтении корпуса, в четырнадцать раз дешевле.

Чем это не является. Правило обязывает не «дёргать graphify перед каждым действием», а не искать вслепую. Обращение к графу не нужно и не считается нарушением, когда:

файл уже назван в распоряжении, промпте или предыдущем шаге — открывай его сразу;
документ входит в обязательное чтение ритма — он читается целиком всегда;
работа идёт с файлом, который агент только что сам и написал.

Лишний вызов инструмента там, где путь уже известен, — такая же трата, как и слепой поиск. Правило про скорость, а не про ритуал.

Три запрета, без которых граф удорожает работу вместо того, чтобы удешевлять:

graph/ops/graph.json и graph/ops/graph.html не открывать инструментом чтения файлов. Это сотни тысяч токенов за один вопрос — дороже, чем прочитать весь репозиторий подряд. Граф читается только командами graphify и через указатель.
Ответ «по графу» без открытого источника не принимается. Узел графа — это пересказ документа, сделанный машиной. Решение принимается по тексту файла.
Указатель, отставший от графа, хуже отсутствующего — он уверенно показывает не туда. После любой пересборки графа обязателен python3 tools/graph_index.py graph/ops/graph.json graph/INDEX.md. Лежит graph/ops/STALE.md — граф старше документов, работай по файлам.

Если graphify в среде не установился — работай по graph/INDEX.md и файлам и заведи это находкой в отчёт: среда, где скил не ставится, чинится, а не обходится молча.

## Приложение. Оригинал §1–4 на языке источника

<details>
<summary>Original wording — приоритет при разночтении перевода</summary>

**1. Think Before Coding.** Don't assume. Don't hide confusion. Surface tradeoffs. Before implementing: state your assumptions explicitly; if uncertain, ask. If multiple interpretations exist, present them — don't pick silently. If a simpler approach exists, say so. Push back when warranted. If something is unclear, stop. Name what's confusing. Ask.

**2. Simplicity First.** Minimum code that solves the problem. Nothing speculative. No features beyond what was asked. No abstractions for single-use code. No "flexibility" or "configurability" that wasn't requested. No error handling for impossible scenarios. If you write 200 lines and it could be 50, rewrite it. Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

**3. Surgical Changes.** Touch only what you must. Clean up only your own mess. When editing existing code: don't "improve" adjacent code, comments, or formatting; don't refactor things that aren't broken; match existing style, even if you'd do it differently; if you notice unrelated dead code, mention it — don't delete it. When your changes create orphans: remove imports/variables/functions that YOUR changes made unused; don't remove pre-existing dead code unless asked. The test: every changed line should trace directly to the user's request.

**4. Goal-Driven Execution.** Define success criteria. Loop until verified. Transform tasks into verifiable goals: "Add validation" → "Write tests for invalid inputs, then make them pass"; "Fix the bug" → "Write a test that reproduces it, then make it pass"; "Refactor X" → "Ensure tests pass before and after". For multi-step tasks, state a brief plan. Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

</details>
