# Универсальный слой запросов: мандат, аудит, гейт

**Полный путь:** `helm/tree/docs/QUERY_LAYER_UNIVERSALITY_2026-09-05.md`
Распоряжение владельца 05.09.2026 · статус: НЕ НАЧАТО, очередь после R8

---

## 0. Что произошло

Пойман архитектурный риск: то, что называется «query router», на деле
вертикальный обработчик одного вопроса — `DOCTORS_VISITED`. Он работает
и принят как первый сквозной срез (§10 `PRODUCTION_ANSWERS_RCA_2026-09-05.md`),
но шаблоном для остальных типов вопросов быть не должен.

Решение владельца дословно по смыслу:

> Текущий кейс врачей не выбрасываем — он остаётся первым end-to-end
> vertical slice и эталоном доказательного ответа. Но больше не
> добавляем doctor-specific архитектуру, если она не является
> необходимой частью общего механизма.

**Прямое следствие для этой сессии: специализация под врачей
остановлена.** Дальнейшие правки в `query_router.py` допустимы только
как часть перевода на общий механизм.

---

## 1. Требования владельца

1. **`QuerySpec`** (или эквивалент) — универсальное представление
   запроса: какие сущности и события ищем; какие связи между ними
   требуются; временные ограничения; группировка и разрешение
   личностей; какие свойства вернуть; требования к доказательствам.
2. **Один executor** на всё:
   `graph/evidence retrieval → canonical identity → temporal filtering
   → deduplication → provenance → result`.
3. **Доменное знание** («врач», «специальность», «посещал») — тонкий
   adapter поверх онтологии, а не собственный обход БД и графа.
4. **`DOCTORS_VISITED` переводится** на общий механизм.
   `DoctorItem`/`DoctorsAnswer` не остаются шаблоном для копирования
   под каждый следующий тип вопроса.
5. **Два существенно разных немедицинских запроса** из разных типов
   знаний проходят тем же executor'ом. Без двух новых
   специализированных роутеров.

**HARD GATE:** врачи и два немедицинских типа вопросов работают через
один и тот же executor. Различаются спецификация запроса и доменный
mapping — не алгоритм поиска, дедупликации, времени и доказательств.
Двух живых немедицинских примеров достаточно; новой тестовой матрицы
не строить.

**Очередь:** R8 → (разбор R4/R4.5, если потребуется) → этот гейт →
только потом допуск R9/R10. До гейта R9/R10 остаются STOP.

## 2. Аудит: что уже универсально, а что действительно вертикально

Замер по `helm_core/knowledge/query_router.py` на HEAD `e71a303`:
692 строки, из них 118 содержат «врач/doctor/специальн». То есть
доменного в файле около шестой части, и это не случайность — большая
часть машинерии уже общая, просто названа по-медицински.

### 2.1. Уже универсальное (переносится почти как есть)

| Что | Роль в будущем executor'е |
|---|---|
| `Proof` | провенанс: источник, окно, точные границы, цитата, ребро |
| `_SourceTexts` | ленивое чтение текстов источников |
| `_spans_for` | упоминания узла с точными спанами |
| `requested_year`, `_split_by_year` | **временной фильтр** — уже не про врачей ни строкой |
| `_answer_in` | слияние графа и доказательств, дедуп по канонической личности, счёт непокрытых |
| `answer_doctors_visited` (каркас) | обход двух схем, отбор живых ревизий, ленивый текст |
| `DoctorsAnswer` (структура) | результат: элементы, пути, счётчики рассмотренного и отброшенного |

### 2.2. Действительно доменное (уходит в adapter/онтологию)

| Что | Чем становится |
|---|---|
| `_DOCTOR_WORD_RE`, `_VISIT_WORD_RE`, `_ENUMERATION_RE` | распознавание намерения → отдельный слой сопоставления вопроса и `QuerySpec` |
| `_HYPHENATED_SPECIALTY_RE`, `_marker_specialty` | правило извлечения АТРИБУТА сущности из её цитаты |
| `doctor_proof` | правило доказательства РОЛИ по маркеру рядом с подписью |
| `role == "doctor"` в `_graph_doctors` | параметр `QuerySpec`: какая роль на ребре требуется |
| фильтр `HAS_ROLE` как «не специальность» | параметр: какие связи считаются подтверждением атрибута |
| `_PERSON_TYPES` | параметр: тип сущности группировки |
| имена `DoctorItem`, `_graph_doctors`, `_evidence_doctors` | `ResultItem`, `_graph_items`, `_evidence_items` |

### 2.3. Смешанное — здесь и есть настоящая работа

`_graph_doctors` и `_evidence_doctors` содержат общий алгоритм
(группировка по личности, однократный обход каждого узла, сбор
доказательств со ВСЕХ узлов личности, отказ от узла без канонической
личности) вперемешку с тремя доменными предикатами. Разделить их —
основная часть задачи; переписывать алгоритм не требуется.

**Честная оценка объёма:** это не переписывание с нуля. Это вынесение
трёх предикатов в параметры, переименование двух функций и одного
dataclass, и появление `QuerySpec` как явного входа вместо неявного
«вопрос про врачей». Заявлять срок не буду, пока не сделан R8: оценка
без замера — та же выдумка, что и дата без доказательства.

## 3. Блокирующая зависимость: немедицинских знаний в корпусе нет

Требование 5 говорит «из РЕАЛЬНОГО корпуса». Замер (прогоны 283, 286,
295): **90 источников, все домена `health`.** Немедицинских источников
в корпусе ноль. Фикстуры R10 (`project_decision`, `purchase_warranty`,
`lecture_concept`) синтетические и откатываются транзакцией, реальным
корпусом они не являются.

Значит, гейт «два живых немедицинских запроса» сегодня физически
невыполним, и это не вопрос кода. Нужно решение владельца — вариантов
вижу два, оба его:

1. **Загрузить в корпус немедицинские документы** (проектные решения,
   покупки и гарантии, конспекты — то, что и так подразумевалось
   доменами `library`/`general`). Тогда гейт выполняется буквально.
2. **Признать фикстуры R10 достаточными** для доказательства
   универсальности executor'а, оставив «на реальном корпусе» до
   появления таких документов. Это слабее: фикстуры писал я, и они по
   построению ложатся на алгоритм.

Мой выбор — первый: смысл гейта именно в том, что данные писал не я.
Но это распоряжение, а не техническое решение.

## 4. Временная ось — универсальная проблема, не медицинская

Отдельно зафиксировано владельцем: провал покрытия по времени
(`occurred_at_start` — 0 из 388 узлов при 104 узлах-событиях) относится
к извлечению знаний вообще, а не к посещениям врачей. Исправление
обязано работать для любого события: покупка, встреча, лекция, приём.

Практически это значит, что чинить надо `semantic_extract`/
`semantic_publish` (гейты заземления R4.5, отбрасывающие дату без
абсолютной даты в цитате), а не добавлять дату в доктора. В R4 без
отдельного решения владельца не идти — это его же ограничение, и оно в
силе.
