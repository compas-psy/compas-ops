# Гейт идемпотентности R6 не может вернуть ноль

Полный путь: `helm/tree/docs/R6_IDEMPOTENCE_GATE_2026-09-05.md`
Прогоны 312 и 313 (`maintenance r6-rebuild.sh`), 05.09.2026.

**Дефект в проверяющем, не в данных.** Гейт `--verify-idempotent` устроен так, что зелёным не станет никогда, сколько ни гоняй.

---

## 1. Что видно в логе

Оба прогона закончились одинаково: `rc=0 idem=1 residue=0`. Пересборка прошла, остаток однословных чист (`no_weak_person_members: true`), идемпотентность провалена.

Сухой проход обоих прогонов:

```
"idempotent": false,
"would_create": { "health.candidates_created": 17 },
"identities_created": 0,
"members_created": 0,
"candidates_by_reason": { "surname_only": 13, "type_conflict": 4 }
```

Создались бы **только строки-кандидаты на ручное разрешение**. Ни одной личности, ни одного члена — граф не поменялся бы.

## 2. Почему это не «не сошлось за один проход»

Такова была моя первая гипотеза, и я её проверил вторым полным проходом. Критерий был назван заранее: `would_create` должен упасть к нулю.

Состояние после обоих прогонов **совпадает до числа**:

| | прогон 312 | прогон 313 |
|---|---|---|
| `identities_total` | 239 | 239 |
| `members_total` | 372 | 372 |
| `candidates_total` | 284 | 284 |
| `person_identities` | 87 | 87 |

Если бы повторный проход действительно создавал 17 строк, `candidates_total` стал бы 301. Он остался 284. **Пересборка идемпотентна — это доказано двумя прогонами.** А сухая проверка всё равно говорит «создал бы».

Гипотеза опровергнута; ходить третий раз бессмысленно.

## 3. Причина, по коду

```
--rebuild            → rebuild_all(session)             (entity_resolution.py:372)
--verify-idempotent  → resolve_all(session, dry_run=True) (entity_resolution.py:499)
```

**Это две разные функции.** Пересборка строит состояние с нуля; проверка делает инкрементальный проход поверх уже построенного. Гейт сравнивает результат одного алгоритма с намерением другого.

Расхождение в 17 строк объясняется тем же: `known_candidates` предзагружается из БД (`entity_resolution.py:165`), то есть дедуп против существующих строк соблюдён, и 17 — это пары, которые инкрементальный проход предлагает, а проход с нуля не порождает вовсе. Разные пути обхода дают разные наборы предложений; ни один из них не «неправильный», они просто разные.

Замечу отдельно: сухой проход к тому же не пишет личности, а значит последующие узлы внутри того же прохода не могут с ними сматчиться и уходят в кандидаты. Симуляция расходится с реальностью by design.

## 4. Что предлагаю — решение за владельцем

Гейт заказан владельцем как жёсткий, поэтому сам я его не трогаю.

1. **Сверять пересборку с пересборкой.** `--verify-idempotent` должен звать `rebuild_all(dry_run=True)`, а не `resolve_all(dry_run=True)`. Тогда проверяется ровно то свойство, ради которого гейт ставился: «повтор той же операции ничего не меняет». По замеру §2 это свойство выполняется, то есть гейт станет зелёным честно, а не послаблением.
2. **Либо сверять состояние, а не намерение.** Снимок счётчиков до и после повторной пересборки; расхождение — провал. Дороже, зато не зависит от того, как устроен сухой режим.

Я за первое: одна строка, и гейт начинает мерить своё имя.

## 5. Долг, найденный попутно

`person_zero_members: 43` при `one_token: 43` — сорок три личности-человека без единого члена, все однословные. Гейт `--verify-no-weak-person-members` их пропускает законно: он ловит однословные личности **с** составом. Пустые личности вреда не делают, но и смысла не несут; в отчёт по врачам они не попадают. Записано долгом, отдельного решения не требует.
