# ADR-021. GigaAM — локальная расшифровка голоса

**Дата:** 31.08.2026 · **Статус:** модель выбрана по живому замеру
(фаза 1), голосовой/видео файл → Knowledge-источник выкачено и
технически подтверждено живьём (фаза 2a), voice-«Запомни» выкачено и
технически подтверждено живьём (фаза 2b) · **Тема §34:**
ADR-021 "Local parser/GigaAM/Ollama Knowledge pipeline" (в части GigaAM
— parser уже реализован раньше, Ollama — отдельный пункт 1.8)

## Область решения

§14.7 требует конвейер `ffmpeg → segmentation/VAD → GigaAM →
timestamped SOURCE`, локально, без платного ASR. §14.10/14.11 отдельно
требуют голосовую версию Micro-Memory: "voice command uses GigaAM
transcription, then Micro-Memory fast path" — то есть голосовое
"Запомни" транскрибируется, но НЕ проходит document-парсинг/чанкинг,
только обычный текстовый Remember-путь. Спека прямо характеризует
GigaAM как **"on-demand worker, not resident daemon model"** —
архитектурно противоположно только что реализованному `helm-embed`
(ADR-025): GigaAM встраивается в уже существующий `helm-knowledge-
worker` (тот же контейнер, что Docling), не отдельным постоянным
сервисом.

§33 запрещает фиксировать модель без замера на живом сервере — та же
причина, что и у ADR-025: офлайн-песочница разработки не подходит
(GitHub git-install и HuggingFace недоступны её egress-политикой).

## Отклонение от документированного API: `transcribe_longform` не используется

Официальный `.transcribe()` работает только на аудио **до 25 секунд**
(проверено чтением исходника репозитория) — голосовые сообщения
Telegram обычно длиннее. Официальный путь для длинных файлов,
`.transcribe_longform()`, тянет `pyannote.audio==4.0.*` для VAD, чья
дефолтная модель сегментации — **`pyannote/segmentation-3.0`, gated на
HuggingFace**: требует владельца лично зайти на HF, завести токен и
принять лицензию. Это `/human`-задача (устав §6, CLAUDE.md §5.2 —
агент не принимает лицензионные соглашения от лица владельца), которая
блокировала бы вообще любой запуск транскрипции до её выполнения —
неприемлемо как обязательное условие базовой функции.

**Решение:** GigaAM ставится БЕЗ extras `[longform]`. Вместо
`pyannote.audio` — **Silero VAD** (MIT, PyPI-пакет `silero-vad`, не
gated, ~2МБ весов) для собственной сегментации длинных файлов на
куски ≤25с; сборка сегментов/таймкодов — в `helm_core`, не в GigaAM
(фаза 2).

## Замер на живом сервере 31.08.2026

Инструмент — `helm_core/knowledge/gigaam_benchmark.py`, внутри уже
существующего образа `Dockerfile.worker` (не отдельный Dockerfile, в
отличие от эмбеддингов — GigaAM и так должна жить в этом образе).
Каждый кандидат — в отдельном подпроцессе (тот же принцип, что
`embed_benchmark.py`: torch не гарантированно освобождает память между
загрузками моделей внутри одного процесса).

Кандидаты — короткие имена из `gigaam._MODEL_HASHES` (прочитано в
исходнике репозитория, не по карточке): `ctc`, `rnnt`, `e2e_ctc`,
`e2e_rnnt` — все расширяются библиотекой до актуальной версии v3,
одного размера (220M параметров). `e2e_*` варианты дополнительно
делают пунктуацию и нормализацию текста (документировано в коде
репозитория).

Реальный результат (два независимых запуска `gigaam-benchmark`, логи в
истории GitHub Actions):

| модель | RSS резидент | загрузка | транскрипция (5с аудио) |
|---|---|---|---|
| ctc | 1545–1549 МБ | 16.5–16.9с | 0.43–0.55с |
| rnnt | 1556–1560 МБ | 11.9–13.8с | 0.53–0.65с |
| e2e_ctc | 1546–1552 МБ | 11.9–12.9с | 0.43–0.49с |
| **e2e_rnnt** | **1562–1564 МБ** | **12.8–13.3с** | **0.75–1.5с** |

RSS практически идентичен у всех четырёх (в пределах шума измерения) —
ожидаемо: одна и та же 220M-параметровая архитектура, разница только в
decoder head и пунктуационной надстройке, не в объёме весов.

### Смысловая проверка не удалась технически — честно зафиксировано, не скрыто

Тестовый файл — синтетическая речь через `espeak-ng` (в контейнере/на
раннере CI нет ни микрофона, ни нейросетевого TTS). **Все четыре
модели вернули пустой или однобуквенный текст** на дефолтных
настройках espeak-ng; после замедления речи (`-s 130` вместо ~175
слов/мин) и нормализации громкости (`ffmpeg -af loudnorm`) результат
не изменился — по-прежнему пустой текст у всех четырёх кандидатов на
втором независимом прогоне.

Это не брак методологии и не повод подгонять вывод: `espeak-ng` —
формантный (Klatt-style) синтезатор, акустически принципиально не
похожий на реальный человеческий голос, на котором обучены
нейросетевые ASR-модели — известное свойство класса, не специфичная
для GigaAM проблема. Дальнейшая подгонка синтетического голоса
(другой TTS, другие параметры) не была предпринята: это увеличило бы
объём работы ради второстепенной проверки, когда решающие для этой
задачи метрики (RSS, латентность) уже получены корректно и
воспроизводимо на двух независимых прогонах.

**Реальная проверка качества распознавания состоится при первом живом
использовании функции** (настоящее голосовое сообщение владельца) —
честно открытый пункт, не скрытый под "протестировано".

## Решение

**e2e_rnnt.**

Основания:

- RSS практически неотличим от трёх других кандидатов (1562–1564 МБ
  против 1545–1560 МБ) — не жертвуем памятью ради архитектурного
  выбора.
- Единственный вариант, сочетающий RNNT-декодер (по документации
  библиотеки — более точный, чем CTC, за счёт авторегрессивного
  декодирования) с пунктуацией/нормализацией текста (`e2e_*`) — важно
  для читаемости итогового Knowledge-источника и для последующего
  лексического/семантического поиска по нему (текст с пунктуацией, не
  голый поток слов).
- Латентность (0.75–1.5с на короткий фрагмент) выше, чем у `ctc`
  (0.43–0.55с), но это on-demand асинхронная задача (владелец получает
  уведомление по готовности, не ждёт в живом чате) — разница в доли
  секунды не значима для этого сценария.

## Фаза 2a — голосовой/видео файл становится Knowledge-источником

Сделано и подтверждено живьём 31.08.2026:

- `helm_core/knowledge/audio.py`: роутинг по расширению в
  `parsers.py::parse_file()` (аудио/видео — ДО MarkItDown/Docling, ни
  один не умеет речь) — конвертация через `ffmpeg` в 16kHz mono WAV,
  сегментация через Silero VAD на куски ≤`MAX_SEGMENT_SECONDS` (24с),
  транскрипция каждого сегмента через `gigaam.load_model("e2e_rnnt")`,
  сборка текста с таймкодами (`timestamped SOURCE`, §14.7). Тот же
  `_quality_ok()` gate, что и у документов — пустая/нераспознанная
  расшифровка эскалирует в `NEEDS_REVIEW` тем же путём, что и плохой
  документ, не отдельная логика.
- `KnowledgeSource.parser = "gigaam"` — поле уже существовало
  (`tables.py` комментарий `markitdown | docling | gigaam | manual`
  предвосхищал это значение), новой миграции не потребовалось.
- Веса модели (`e2e_rnnt`) запекаются в `Dockerfile.worker` на сборке
  (тот же приём, что `HF_HOME` у `helm-embed`/ADR-025) — GigaAM
  использует собственный `download_root`, не HuggingFace cache.
- 15 тестов (`test_knowledge_parsers.py`): роутинг по расширению,
  `parse_file()` вызывает `transcribe_audio()` для аудио, quality gate
  на транскрипте — `transcribe_audio()` мокается, реальная модель не
  доступна в тестовом окружении control-plane.

**F-260831-03** (найдено первым же живым прогоном): `torchaudio.load()`
в свежих версиях (>=2.9) делегирует на `torchcodec`, которого нигде не
было — `ModuleNotFoundError` на первом же вызове. recon-скрипт при этом
отчитался `success`: `set -uo pipefail` без `-e` не остановился на
ошибке `docker compose run`, дошёл до конца и вернул код последней
команды (`rm` временного файла) — тот же класс "зелёный при упавшем
сервисе", что уже был 30.08.2026 с `helm-core`. Исправлено: `torchcodec`
добавлен в общую команду установки torch-пакетов (FFmpeg
shared-библиотеки для него уже есть через apt), recon-скрипт получил
`-e` + `trap ... EXIT`. Передеплоено и перепроверено:

```
parser: gigaam
quality_ok: False
elapsed_seconds: 11.13
text: ''
```

Конвейер (ffmpeg → Silero VAD → GigaAM) отработал технически чисто за
11.13с без исключений — то же ограничение методологии, что и у
бенчмарка (espeak-ng акустически нераспознаваем нейросетевыми ASR, см.
выше): `quality_ok=False` на нераспознанном входе — не поломка, а
gate сработал ровно так, как спроектирован. Живая проверка на
настоящей человеческой речи (не synthetic espeak-ng) — при первом
реальном использовании функции, тот же честно открытый пункт, что и
для выбора модели в фазе 1.

## Фаза 2b — voice-«Запомни»

Сделано 31.08.2026. Раньше **любое** голосовое вложение уходило в
document-ingest путь (`chat_intake.py::stage_attachment` → domain-меню
→ `KnowledgeIngestJob` → `worker.py::parse_file()`), даже если по
смыслу это голосовая команда "Запомни". Решение "это Remember или
документ" можно принять только ПОСЛЕ транскрипции — асимметрично
document-флоу (который спрашивает домен СИНХРОННО, до обработки).

Реализовано:

- `KnowledgePendingAttachment` — три новых поля (миграция
  `9c3f1d4b7a2e`): `kind` (`document`/`voice`, определяется по
  расширению файла в `stage_attachment()` — тем же `is_audio_file()`,
  что уже роутит `parsers.py`), `transcript` (`NULL` = "ещё не
  транскрибировано" для voice, "не применимо" для document),
  `recipient` (адресат для АСИНХРОННОГО уведомления воркера — тот же
  паттерн, что уже был у ZIP-batch).
- `stage_attachment()` для voice НЕ отправляет меню доменов сразу —
  `stage_outcome_text()` возвращает `VOICE_STAGED_NOTICE`
  ("расшифровываю, отвечу через несколько секунд") вместо
  `format_domain_menu()`.
- `audio.py::strip_timestamps()` — убирает построчные таймкод-префиксы
  `[Ns] ` перед проверкой на Remember-триггер: `detect_remember_command()`
  матчит только с самого начала строки, а `transcribe_audio()` всегда
  начинает вывод с таймкода (§14.7) — без этой очистки "Запомни" в
  первой строке транскрипта никогда бы не совпало с триггером.
- `worker.py::claim_next_voice_pending()`/`process_voice_pending()` —
  тот же round-robin fair-queue, что `claim_next_job()`, отдельным
  индексом, опрашивается ПОСЛЕ document-job'ов в `run_forever()`.
  `process_voice_pending()`: `transcribe_audio()` → `strip_timestamps()`
  → `try_remember(origin_kind="voice")` → если это Remember-команда,
  подтверждение владельцу и pending удаляется (файл в spool больше не
  нужен); если нет — `pending.transcript` сохраняется, и владелец
  получает предпросмотр распознанного текста + тот же вопрос о домене,
  что и для документа (`voice_ready_menu_text()`).
- `resolve_pending_domain()` пропускает voice-pending, пока `transcript
  IS NULL` — ответ владельца, пришедший до завершения транскрипции, не
  может быть ошибочно понят как ответ на домен для ещё не готового
  файла.
- Владелец подтвердил (31.08.2026): голосовой документ обязан пройти
  ЧЕРЕЗ ТОТ ЖЕ пайплайн индексации, что и текстовый — "мы все документы
  потом превращаем в индекс (Graphify)". Реализовано буквально:
  не-Remember voice, после выбора домена, идёт через СУЩЕСТВУЮЩИЙ
  `register_file_for_ingest()` → `process_job()` → `parse_file()` →
  `transcribe_audio()` путь на физически перенесённом аудиофайле — тот
  же код, что обрабатывает любой документ, без отдельной "урезанной"
  ветки для голоса.
- **Сознательный компромисс (простота важнее эффективности,
  CLAUDE.md §2):** не-Remember voice транскрибируется ДВАЖДЫ — один
  раз в `process_voice_pending()` для проверки Remember-триггера, ещё
  раз обычным document-пайплайном после выбора домена. Альтернатива
  (передавать уже готовый транскрипт в `KnowledgeIngestJob`, минуя
  повторный `parse_file()`) потребовала бы нового поля в схеме job'а
  ради ~11с фонового вычисления, которое ни на что не влияет
  асинхронно — решение сознательно в пользу переиспользования
  существующего кода, а не микрооптимизации.
- `hooks.py` (MAX)/`internal.py` (Telegram)/`hermes-control` —
  `recipient` прокинут через стадию staging тем же путём, что уже есть
  у ZIP-batch (`_stage_batch()`/`_handle_batch_attachment_async()`).
- Тесты (локально, 30 новых/изменённых): `strip_timestamps()`,
  `kind`-детекция и ветвление `stage_outcome_text()`/
  `voice_ready_menu_text()`, пропуск нетранскрибированного voice-pending
  в `resolve_pending_domain()`, `claim_next_voice_pending()`
  round-robin, `process_voice_pending()` — Remember-ветка,
  не-Remember-ветка, провал транскрипции (не должен ронять воркер),
  отсутствие recipient (не должен слать в outbox), endpoint-уровень
  (Telegram HTTP + MAX webhook) — `transcribe_audio()` мокается
  (реальная модель недоступна в тестовом окружении control-plane).

**F-260831-04** (найдено этим же прогоном, до успеха — два реальных
бага подряд, не гипотетических): (1) первая версия `verify-voice-

`FileNotFoundError`, разные файловые системы; recon-действие в
`deploy.yml` (портировано с `main`) при этом отчиталось `success` —
`ssh 'bash /tmp/recon.sh \n rm -f ...'` без `&&`/явного `exit $?` терял
код возврата упавшего скрипта, тот же класс маскировки, что уже был у
F-260831-03. (2) После исправления декодирования (напрямую в
контейнер через stdin) — НОВЫЙ реальный сбой, уже не скрипта:
`PermissionError` на `mkdir /opt/helm-state` внутри
`helm-knowledge-worker`. Причина — пробел в `docker-compose.yml`:
`/opt/helm-state/knowledge-spool` смонтирован только в `helm-core`
(P8.5.7, там вызывается `stage_attachment()`), а НЕ в
`helm-knowledge-worker` — но именно `process_voice_pending()` читает
`pending.spool_path` для транскрипции. Это НЕ артефакт recon-скрипта:
КАЖДОЕ реальное voice-сообщение в проде упало бы `FileNotFoundError`
на первом же вызове `transcribe_audio()`, обнаружено только потому,
что recon попытался воспроизвести полный цикл живьём. Исправлено:
volume добавлен в `helm-knowledge-worker` (`group_add: ["1001"]` там
уже был), `ssh`-обёртка recon-действия получила `rc=$?; ...; exit $rc`.
Передеплоено, recon переписан на два контейнера (staging — в
`helm-core`, где смонтирован spool; `process_voice_pending()` — в
`helm-knowledge-worker`, где GigaAM), перепроверено.

Финальный чистый прогон (`scripts/verify-voice-remember-pipeline.sh`):
`stage_attachment()` в `helm-core` → `process_voice_pending()` напрямую
в `helm-knowledge-worker` (без `claim_next_voice_pending()` — чистый
round-robin, уже покрыт локальными юнит-тестами) на тестовом `.ogg`
(тот же файл, что у фазы 2a). `recipient` не передавался — ни один
боевой канал не получил тестовое сообщение, тестовая pending-строка
удалена тем же скриптом (cleanup внутри process_voice_pending()-ветки).

```
staged kind: voice
staged sha256 matches: True
d975d1b0-4a51-4787-b761-fd62db325768
outcome: document-branch (pending остаётся)
transcript: ''
cleanup done
```

Ни одного исключения по всему логу шага — конвейер (staging → два
разных контейнера → GigaAM → try_remember() → ветвление → cleanup)
отработал технически чисто. `transcript: ''` — то же самое
методологическое ограничение, что уже задокументировано выше и в фазе
2a (espeak-ng акустически нераспознаваем нейросетевыми ASR): пустой
транскрипт не совпадает с Remember-триггером (`detect_remember_command`
возвращает `None` на пустой строке), поэтому корректно ушёл в
document-branch — то же поведение, которое ожидалось бы от НАСТОЯЩЕГО
не-Remember голосового сообщения. Живая проверка РЕАЛЬНОГО распознавания
(включая срабатывание Remember-ветки на настоящую фразу "Запомни ...")
— при первом живом использовании владельцем, тот же честно открытый
пункт, что и у фазы 1/2a.
