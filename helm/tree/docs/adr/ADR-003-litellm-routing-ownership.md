# ADR-003. LiteLLM routing ownership

**Дата:** 31.08.2026 · **Статус:** реализовано и стабильно работает
(статическая конфигурация); динамическая эскалация по типу вопроса —
осознанно отложена, не блокирует эту часть.

## Контекст

Несколько профилей Hermes и Control Plane нуждаются в LLM, но ни один
компонент не должен сам решать, к какому провайдеру идти и с каким
ключом — иначе платный ключ размножается по местам, которые его не
должны видеть.

## Решение

**Статическая конфигурация LiteLLM, ownership — у инфраструктуры, не у
кода.** Ни Hermes, ни Control Plane не выбирают провайдера/модель в
рантайме — они запрашивают фиксированный алиас, а провайдер/фоллбэк/
ретраи целиком описаны в `config/models/litellm.yaml`, зафиксированном в
репозитории.

### Hermes видит только алиасы, не ключ

`litellm.yaml` (комментарий): «Алиасы — единственное, что видит Hermes
(§15.4): прямого `OPENROUTER_API_KEY` у Hermes нет и не будет.»
`scripts/provision_hermes_profiles.sh` — каждому профилю Hermes выдаётся
один scoped LiteLLM virtual key, привязанный ровно к одному алиасу
(`PROFILE_ALIAS`) — профиль физически не видит остальные алиасы, не
только не должен их использовать по конвенции.

### Control Plane не трогает LiteLLM вообще

`helm_core/` нигде не вызывает LiteLLM напрямую (грепом по кодовой
базе). Единственный AI/ML-вызов Control Plane — локальный embedding-
сервис, и тот отдельно документирован как изолированный:
`embed_service.py`: «Никаких секретов не получает и никуда не стучится,
кроме своего порта — доступа ни к LiteLLM/OpenRouter credentials, ни к
базе».

### Провайдер/фоллбэк — decision живёт в конфиге, не в коде

Выбор основного провайдера, порядок фоллбэков (`router_settings.
fallbacks`), ретраи, особенности `drop_params` — всё в статическом,
закоммиченном `litellm.yaml`, не решается ни одним компонентом во время
запроса.

## Не в объёме этого захода

**Динамическая маршрутизация по типу вопроса — отложена, не решена.**
`WORKPLAN.md` фиксирует прямое owner-решение: маршрутизация чата chief
сегодня жёстко закреплена за `helm-standard` безусловно, не по
классификации сообщения; «Динамическая эскалация... отдельная, более
крупная задача, отложена до Milestone B/C, не делалась сегодня.» Если
исходный вопрос спеки был именно про ownership ДИНАМИЧЕСКОГО решения "к
какой модели эскалировать" — эта часть открыта, не закрыта этим ADR:
здесь зафиксирован только статический, уже реализованный ответ (кто
владеет конфигурацией провайдеров), не решение по классификации
сообщений в реальном времени.
