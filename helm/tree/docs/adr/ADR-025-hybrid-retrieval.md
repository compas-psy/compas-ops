# ADR-025. Global-within-user hybrid retrieval — выбор embedding-модели

**Дата:** 31.08.2026 · **Статус:** модель выбрана по живому замеру, схема
и wiring в процессе · **Тема §34:** ADR-025 "Global-within-user hybrid
retrieval"

## Область решения

§14.12 требует единый пайплайн поиска:

```text
query
→ exact memory/source metadata lookup
→ Micro-Memory FTS/vector
→ document chunk FTS/vector
→ canonical relations
→ optional per-user Graphify
→ deterministic rank fusion
```

До этого ADR у Probe (`probe.py`, §14.11-13) был только лексический слой
(`ts_rank` на `tsvector`, см. ADR-009 в части исполнения RED-действий —
нет, точнее см. сам `probe.py`): перефразированный вопрос без общих со
источником словных корней не находился вовсе. §33 прямо запрещает
фиксировать embedding-модель без замера на живом сервере ("P8.5 ...
local embeddings ... still require resource/quality benchmark") —
офлайн-песочница разработки для этого не подходит: HuggingFace
заблокирован её egress-политикой (тот же ограничитель, что уже был для
Docling, см. `docker-compose.yml` комментарий у `helm-knowledge-worker`).

## Замер на живом сервере 31.08.2026

Инструмент — `helm_core/knowledge/embed_benchmark.py`, отдельный образ
`Dockerfile.embed` (CPU-only torch + sentence-transformers, без Docling/
opencv воркера и без FastAPI/torch у helm-core — лимит helm-core 768MB
не оставляет места резидентной модели). Каждый кандидат гонялся в
ОТДЕЛЬНОМ подпроцессе — torch не гарантированно освобождает память между
загрузками моделей внутри одного процесса, замер RSS без изоляции был бы
недостоверным.

Мерилось: память резидентно (VmRSS после инференса), латентность (пакет
из 30 синтетических текстов и один текст — эмуляция ingest и одиночного
вопроса на Probe), и минимальная проверка смысла на русском — четыре
пары "вопрос — идентичный по смыслу ответ БЕЗ общих словных корней"
против отвлекающего текста на другую тему (не полноценная IR-оценка на
golden-set — честная пометка в самом выводе инструмента).

Реальный результат (запуск `embed-benchmark`, лог сохранён в истории
GitHub Actions):

| модель | dim | RSS резидент | загрузка | пакет-30 | 1 текст | смысл |
|---|---|---|---|---|---|---|
| intfloat/multilingual-e5-small | 384 | 894.7 МБ | 21.0с | 0.834с | 23мс | 4/4 |
| intfloat/multilingual-e5-base | 768 | 1125.5 МБ | 27.2с | 1.909с | 53мс | 4/4 |
| **sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2** | **384** | **854.0 МБ** | **19.8с** | **0.756с** | **25мс** | **4/4** |
| BAAI/bge-m3 | 1024 | 1972.2 МБ | 54.7с | 14.931с | 215мс | 4/4 |

Все четыре прошли минимальную проверку смысла 4/4, но не одинаково
уверенно. У E5-семейства (small/base) похожесть на позитивный и на
отвлекающий текст сжаты в узкий диапазон 0.68–0.85 — разница есть, но
калибровать по ней абсолютный порог (по образцу уже откалиброванного
`MIN_RANK_SCORE=0.003` у лексического поиска) сложнее: узкий зазор
чувствителен к шуму. У MiniLM разделение чистое: позитив 0.20–0.55,
негатив от -0.04 до 0.01 — то есть по факту ортогонально для несвязанных
тем. Это не гипотеза о будущем golden-set, а прямое свойство самого
распределения косинусов на этом замере.

## Решение

**sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2, dim=384.**

Основания, все по факту замера, не по карточке модели:

- Минимальный резидент (854 МБ) из четырёх — при бюджете 12 ГБ на весь
  сервер (§4.1) и уже занятых 9.536 ГБ текущими сервисами (postgres 3g +
  litellm 1g + helm-core 768m + worker 3g + n8n 1g + forgejo 512m +
  caddy 256m) свободно ~2.46 ГБ. Постоянный сервис на этой модели
  оставляет ~1.5 ГБ запаса, а не съедает всё до предела.
- Самая быстрая латентность на пакет и на одиночный текст среди всех
  четырёх — важно для Probe: это pre-LLM gate, каждый обычный вопрос
  проходит через него ДО платной модели, лишние 200мс на эмбеддинг
  запроса (как у bge-m3) были бы заметны в живом диалоге.
- Единственная модель с чисто разделёнными похожестями на этом замере —
  практическое свойство, которое напрямую упрощает калибровку порога
  отсечения (следующий шаг, тот же принцип, что уже применён к
  `MIN_RANK_SCORE`).
- BAAI/bge-m3 — явно избыточен для этой задачи: в 10 раз медленнее на
  одиночный вызов и вдвое тяжелее по памяти при той же оценке 4/4 на
  этом тесте, без компенсирующего выигрыша в качестве, который было бы
  чем измерить здесь. Не выбран.

Размерность 384 фиксирует форму будущей pgvector-колонки
(`knowledge_chunks.embedding vector(384)`) — совпадает с
`intfloat/multilingual-e5-small`, но это совпадение размерности не имеет
отношения к причине выбора MiniLM.

## Что сделано (стенд замера)

- `control-plane/Dockerfile.embed` — отдельный образ.
- `helm_core/knowledge/embed_benchmark.py` — инструмент замера, не
  сервис (тесты кандидатов гоняются подпроцессами).
- `docker-compose.yml::helm-embed` — build-only до этого решения, теперь
  становится постоянным сервисом (следующий коммит).
- Действие `embed-benchmark` в `deploy.yml`, самодостаточное (доставляет
  само себе `helm_core`/`Dockerfile.embed`/`docker-compose.yml`, не
  зависит от предшествующего `deploy`).

## Что дальше (эта же задача, в процессе)

- Постоянный сервис `helm-embed` (HTTP `/embed`, модель резидентна) —
  helm-core и воркер зовут его по HTTP, ни один не тянет torch в свой
  образ (768MB лимит helm-core, воркер — уже занят Docling).
- Миграция: `CREATE EXTENSION vector` + `knowledge_chunks.embedding
  vector(384)` + индекс (ivfflat/hnsw — выбор индекса отдельным
  подпунктом, не блокирует сам столбец).
- `worker.py`: эмбеддинг чанка при ingest, рядом с уже существующим
  `tsv = to_tsvector(...)`.
- `probe.py`: hybrid FTS + pgvector с детерминированным rank fusion
  (§14.12), а не заменой лексического слоя.
- Backfill эмбеддингов для уже существующих чанков.
- Тесты tenant-изоляции векторного поиска — тот же бар, что уже держит
  FTS (§30.8.5: "cross-user pgvector result 0"), RLS + service-layer
  negative test.
