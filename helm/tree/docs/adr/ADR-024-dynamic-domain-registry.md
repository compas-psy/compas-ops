# ADR-024. Реестр доменов: узкий срез динамической таксономии

**Дата:** 31.08.2026 · **Статус:** выкачено и подтверждено на уровне
схемы/RLS; диалог бота живьём не проверялся (решение владельца) ·
**Тема §34:** ADR-024 "Scalable dynamic Knowledge taxonomy"

## Область решения

§14.5 ТЗ описывает динамическую таксономию из четырёх частей:

```text
knowledge_domains          — сделано этим ADR
knowledge_topics           — не делается сейчас
knowledge_topic_aliases    — не делается сейчас
knowledge_source_topics    — не делается сейчас
```

Реализована только первая часть — сам реестр доменов вместо жёсткого
списка из 11. Topics/aliases/source_topics осмысленны только вместе с
Graphify (P8.5.6, ещё не реализован, ждёт замера на живом сервере) — без
него это была бы схема без потребителя. Решение владельца 31.08.2026:
делать реестр доменов сейчас, версии источников (D2 в §14.7) отложить до
локальных embeddings (P8.5.4 хвост, тоже ждёт сервера) — те два дела
были одним пунктом хвоста B.5 (1.5 в `ROADMAP-TO-DONE.md`), разделены на
разные сроки.

## Что было раньше

`KnowledgeDomain` — Python `StrEnum` из 11 значений (плюс `library`,
добавлен решением владельца 29.08.2026). Диалог выбора домена
(`chat_intake.py::parse_domain_reply()`) принимал только номер из этого
списка, точное совпадение имени или короткий алиас. Любое другое имя —
`invalid`, меню повторялось. Заводить новый домен значило редактировать
код и выкатывать.

## Что сделано

Встроенный `KnowledgeDomain` остаётся: на нём держится защитная
семантика (`simpas/zapiski` принудительно получает `client_restricted`
sensitivity в `chat_intake.py`/`batch_intake.py` — привязка к конкретным
Python-значениям, не то, что можно превратить в произвольную строку без
потери гарантии).

Добавлена таблица `knowledge_domains` (ORM: `KnowledgeCustomDomain`,
миграция `8b2f4e7a1c93`) — per-user, под RLS, как и остальные
tenant-scoped таблицы:

```text
id, knowledge_user_id, key, use_count, created_at, last_used_at
UNIQUE (knowledge_user_id, key)
```

`domain` остаётся простой строкой везде, где был (`KnowledgeSource`,
`KnowledgeMemory`, `KnowledgeIngestBatch`) — не FK на реестр. Это уже
было решено раньше для `KnowledgeMemory.domain` (см. комментарий в
`models/tables.py`) и здесь просто не нарушается.

Диалог выбора домена (`chat_intake.py`, `batch_intake.py`) теперь
принимает набранное имя, которого нет ни во встроенном списке, ни в
реестре пользователя, как **запрос создать новый домен**, а не как
ошибку — с двумя условиями:

- длина ≤ 32 символов (лимит колонки `domain` везде в схеме);
- один токен, без пробелов (ни один встроенный домен не содержит
  пробела — многословный ответ читается как непонятый текст, не как имя
  домена).

Повторный ввод того же имени (регистронезависимо) не заводит вторую
строку — увеличивает `use_count` у существующей. Меню показывает
встроенные домены первыми в неизменном порядке (владелец уже помнит их
номера), затем — домены пользователя, отсортированные по частоте и
свежести использования.

## Почему не "silent creation from one document"

§14.5 отдельно запрещает молча заводить постоянный домен по одному
документу. Здесь домен создаётся только явным текстовым ответом на
прямой вопрос меню ("В какой домен положить? Ответьте номером или
именем") — то есть решение принимает человек в моменте разговора, а не
эвристика, угадывающая домен по содержимому файла. Ни бот, ни воркер
никогда не создают домен сами.

## Что сознательно не сделано

**Топики/сущности/связи.** Требуют Graphify, которого нет. Делать схему
раньше значило бы держать таблицы без потребителя — и почти наверняка
переделывать их формат, когда Graphify наконец появится и станет ясно,
что ему реально нужно от структуры топиков.

**Пагинация меню ("recent/most-used" + "Ещё").** §14.5 описывает меню
как короткий список последних/частых доменов с раскрытием по "Ещё".
Реализовано проще: полный список встроенных (как было) плюс список
пользовательских — без обрезки и кнопки "показать ещё". Для одного
активного пользователя с разумным числом доменов разница не ощущается;
если список пользовательских доменов вырастет настолько, что меню
станет неудобным, обрезка добавляется отдельно — это чисто
косметический слой поверх уже работающего реестра, не структурная
переделка.

**Panel UI для управления доменами.** Пока домены заводятся только через
бот; панель их не показывает и не позволяет переименовывать/сливать.
Отдельная задача, не блокирующая сам реестр.

## Тесты

`tests/test_knowledge_chat_intake.py`: создание нового домена явным
ответом, появление в меню под следующим номером, повторное использование
без дублирования строки, выбор по номеру меню, tenant-изоляция реестра
между двумя пользователями (RLS), отказ на слишком длинном имени, отказ
на многословном тексте (сохраняет старое поведение "not a domain" →
invalid). 486 тестов зелёных, было 480 до этого ADR.

## Живой сервер

Выкачено 31.08.2026 (ветка `claude/ai-agents-server-deployment-xdp77a`,
коммит `cbbff79`). Миграция `8b2f4e7a1c93` накатилась на проде без
происшествий. Действие `migrate` подтвердило: схема на голове, роль
приложения `helm_app` без `rolsuper`/`rolbypassrls`, `knowledge_domains`
в списке из одиннадцати tenant-таблиц с RLS — включена, форсирована,
ровно одна политика, строк без владельца нет.

Первый заход упал по причине, не связанной с самим реестром: код ветки
попутно завёл RED-действие `delete_knowledge_user` (более ранний коммит
этого же цикла), запись для которого в `config/policies/actions.yaml`
была в git, но не на сервере — выкат никогда не доставлял этот файл
(подробности и починка — `ROADMAP-TO-DONE.md`, «Что нашёл живой выкат
31.08.2026»). Простой был коротким: helm-core ушёл в `Restarting` в
пределах одного и того же workflow, следующий запуск с починенным
деплоем поднял его штатно.

**Не проверено:** сам диалог бота живьём — что старые номера меню
по-прежнему принимаются и что набранное вручную имя домена доезжает до
следующего меню. Owner-решение этого цикла — Knowledge-бота сейчас не
трогать; это отложено, а не забыто.
