# ADR-030. Tenant isolation: user key + RLS + no cross-user dedup

**Дата:** 31.08.2026 · **Статус:** реализовано и подтверждено живьём
30.08.2026 (ROADMAP-TO-DONE.md блок 0, действие `migrate`): все
tenant-таблицы — RLS включена и форсирована, ровно одна политика на
каждой, роль `helm_app` не суперпользователь и не BYPASSRLS.

## Контекст

§14.4 требует "PostgreSQL defense in depth" — изоляция между
пользователями не должна держаться только на том, что код нигде не
забудет дописать `WHERE knowledge_user_id = ...`. Один забытый предикат
в одном запросе — утечка чужого Second Brain.

## Решение

**Два независимых слоя, оба обязаны сработать.**

### Слой 1 — явный предикат в коде

Каждый существующий query в `ingest.py`/`probe.py`/`worker.py`/... несёт
`knowledge_user_id = ...` явно. Это первый и самый быстрый слой, но
единственный слой — предположение, что ни один будущий код никогда не
забудет его дописать.

### Слой 2 — PostgreSQL RLS, FORCE, а не только ENABLE

`helm_core/knowledge/rls.py::apply_rls_to_table()` — `ALTER TABLE ...
FORCE ROW LEVEL SECURITY`, не только `ENABLE`: без `FORCE` Postgres не
применяет RLS к владельцу таблицы, а таблицами владеет та же роль
(`helm_app`), что обслуживает рантайм — без `FORCE` политика была бы
декорацией. `TENANT_SCOPED_TABLES` — единственный список, общий для
Alembic-миграции (`4da8c9e90115_knowledge_rls.py`) и тестовой фикстуры
(`conftest.py`), чтобы pytest проверял ровно те же политики, что накатаны
в проде, не отдельный список, который может разойтись.

Предикат один на все таблицы:

```sql
knowledge_user_id = NULLIF(current_setting(
  'app.current_knowledge_user_id', true), '')::uuid
```

`current_setting(..., true)` — `missing_ok=true`, вернуть NULL, не
упасть, если GUC ещё не выставлен этой транзакцией. `NULLIF(..., '')`
закрывает конкретный найденный живьём класс бага: на пуле соединений
once custom GUC тронут `SET LOCAL` хотя бы раз за время жизни физического
соединения, Postgres заводит для него placeholder `''` (пустая строка),
не NULL — следующая транзакция на том же соединении без явного
`bind_knowledge_user()` видит `current_setting(...) = ''`, и `''::uuid` —
ошибка кастинга (падение запроса), не NULL. `NULLIF` нормализует обе
формы ("не тронуто вовсе" и "тронуто раньше, не тронуто сейчас") к
одному NULL — тогда `knowledge_user_id = NULL` даёт NULL (fail closed:
ни одной строки), а не падение запроса.

`bind_knowledge_user()` (`tenancy.py`) — единая точка входа: разрешает
тенанта (SYSTEM_OWNER по умолчанию) И сразу привязывает GUC одним
вызовом, чтобы предикат в коде и GUC для RLS никогда не разошлись.
Обязателен на каждом входе в транзакцию, которая трогает tenant-scoped
таблицу — без него политики видят GUC как NULL и не отдают ни одной
строки.

`knowledge_users`/`channel_identities`/`invites`/`user_usage` — НЕ
tenant-scoped (реестр тенантов, не их контент — RLS на них не имеет
смысла: они и есть таблица, по которой RLS остальных решает
принадлежность).

### No cross-user dedup — уникальность по паре, не по одному хэшу

`KnowledgeSource.sha256` — уникальность по `(knowledge_user_id, sha256)`,
НЕ по одному `sha256`. §14.2 явно запрещает cross-user dedup: "user A
content != user B content ... no shared chunk-set or content-existence
side channel". Глобальная уникальность отдала бы User B готовый source
User A просто по совпадению байт — тот же файл, загруженный дважды
разными людьми, породил бы две независимые строки, а не одну
переиспользованную.

## Не в объёме этого захода

- Множественные роли/уровни доступа внутри одного тенанта (например,
  "секретарь владельца с ограниченным доступом к части Vault") — модель
  сегодня знает только границу между тенантами, не роли внутри одного.
