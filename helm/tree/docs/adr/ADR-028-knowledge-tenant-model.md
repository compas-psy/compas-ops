# ADR-028. Knowledge tenant model: SYSTEM_OWNER vs KNOWLEDGE_USER

**Дата:** 31.08.2026 · **Статус:** реализовано и задеплоено v3.8 Фаза 1,
подтверждено живьём 30.08.2026 (ROADMAP-TO-DONE.md блок 0: RLS
включена/форсирована на всех tenant-таблицах, роль `helm_app`
`rolsuper=f`/`rolbypassrls=f`).

## Контекст

До v3.8 весь Second Brain принадлежал одному владельцу неявно — ни
одной строки `knowledge_user_id` в схеме не было. §14.2 вводит
многопользовательский Second Brain: секондари-пользователи со своим
изолированным хранилищем, БЕЗ доступа к остальному HELM (Hermes,
Control Plane, чат-боту владельца).

## Решение

**Одна таблица `knowledge_users` с ролью, не два разных бэкенда.**
`KnowledgeUser.role` — `SYSTEM_OWNER` (ровно одна строка, backfill
существующих данных при миграции `ef1ba5467e14`) или `KNOWLEDGE_USER`
(новые, заводятся через инвайт, ADR-029). Общая схема, общий код
(`ingest.py`/`probe.py`/`worker.py` не различают роль в логике
обработки) — разница между ролями выражена не веткой if, а тем, ЧТО
физически достижимо:

- `allow_paid_ai: bool = False` по умолчанию — §14.1: KNOWLEDGE_USER по
  умолчанию НЕ может дойти до платной модели вообще, вызывающий код
  обязан проверить этот флаг до любой попытки эскалации к Hermes/
  OpenRouter, а не полагаться на то, что секондари-путь "просто не
  умеет" эскалировать.
- Отдельный Telegram bot/webhook для `KNOWLEDGE_USER` (ADR-029) — не
  расширение owner chief bot. `KNOWLEDGE_USER` физически не может дойти
  до Hermes/LiteLLM тем же способом, что и владелец: этот модуль их не
  импортирует вовсе, "never reaches Hermes by construction".
- RLS (ADR-030) — оба типа тенанта видят СВОИ строки и только их, включая
  `SYSTEM_OWNER`: привилегия "видеть всё" не выражена как обход RLS ни
  для одной роли БД, только явным `bind_knowledge_user()` на нужного
  тенанта в коде.

### `resolve_system_owner_id()` — явная ошибка, не тихое создание второй строки

`tenancy.py::resolve_system_owner_id()` требует РОВНО одну строку
`role=SYSTEM_OWNER` и падает явной ошибкой, если её нет — не создаёт
вторую владельческую строку молча. Существующие call sites
(`ingest.py`/`chat_intake.py`/`batch_intake.py`/`probe.py`/`worker.py`),
которые не передают `knowledge_user_id` явно (весь код, написанный до
Dedicated Knowledge Bot, P8.6.2), разрешаются в этого единственного
владельца — обратная совместимость без ветвления кода: старые call
sites просто продолжают работать, как будто KNOWLEDGE_USER никогда не
появлялся.

### Стиль и роль — двойной гейт, не только версия

`style.py::_owner_style_prompt_or_none()` (docstring, `rephrase.py`) —
персональный стиль владельца (Z2-рефраз) применяется не только по
`style_profile_version`, но и по проверке `role == SYSTEM_OWNER`: сам
номер версии не идентифицирует ЧЕЙ это стиль — второй KNOWLEDGE_USER с
тем же номером версии не получил бы чужой стиль по случайному
совпадению числа.

## Не в объёме этого захода

- Panel-приглашение/passkey для `KNOWLEDGE_USER` (§14.3 "Panel onboarding
  for KNOWLEDGE_USER") — ждёт P8.6.5.
- Множественные `SYSTEM_OWNER` (co-owner) — спека и код предполагают
  ровно одного; не запрошено, не реализовано.
