# ADR-016. Panel Telegram Login + WebAuthn (спека предлагала OIDC)

**Дата:** 31.08.2026 · **Статус:** реализовано, задеплоено, живьём
подтверждено («панель с passkey» — Milestone B "Работает").

Название темы в спеке — «Panel Telegram OIDC + WebAuthn». Реализовано
другое: **Telegram Login Widget, не OIDC** — задокументированное
отклонение, тот же прецедент, что уже зафиксирован для ADR-017/018
(решение принято противоположное тому, что предполагала спека).

## Контекст

§10.5.6-§10.5.8.2 описывают вход в Panel: подтверждение личности через
Telegram, затем WebAuthn/passkey для самой сессии и для step-up на
запись. Спека называет OIDC (Authorization Code+PKCE) предпочтительным
способом телеграм-подтверждения.

## Решение

### Почему не OIDC — проверено вживую, не предположение

`api/auth.py` (docstring, дословно): «Спека называет предпочтительным
способом OIDC..., но для этого бота он у BotFather недоступен (проверено
вживую 29.08.2026: "Web login is currently unavailable", а после
привязки домена открывается документация только classic-виджета) —
используется официальный, но более старый механизм Telegram с проверкой
HMAC-подписи на самом токене бота.»

`WORKPLAN.md` фиксирует само расследование: `/mybots → Bot Settings →
Domain` сначала отвечал «Web login is currently unavailable»; после
`Set domain → helm.cmpas.ru` стало доступно, но экран предложил только
документацию classic Telegram Login Widget — ни разу не показал пункт
«OpenID Connect Login» или Client ID/Secret. Решение: не ждать и не
гадать, перейти на classic Login Widget (тот же официальный механизм
Telegram, HMAC-SHA256 подпись на самом bot token, годами стабилен).
Серверная часть после Telegram-подтверждения не зависит от того, каким
именно способом подтверждён `sub`/`id` — если Telegram позже раскатит
OIDC на этого бота, вернуться можно будет без переделки остального.

### Три потока, один модуль

`auth.py` (docstring): 1) Telegram Login Widget подтверждает, что за
браузером сидит владелец (HMAC-подпись на токене бота); 2) первый
enrollment passkey (§10.5.7) — единственный путь получить первый
`WebauthnCredential`, когда его ещё ни одного нет, гейтится одноразовым
`PanelEnrollmentToken` (хэш в БД, TTL); 3) passkey-логин и passkey
step-up на запись (§10.5.8/§10.5.8.1) — `/auth/passkey/assert/*`, JSON-
контракт зафиксирован фронтендом (`panel/src/components/passkey.ts`),
написанным раньше этого модуля.

Переходное состояние «Telegram подтвердил, passkey ещё нет» — подписанная
cookie на 10 минут, НЕ отдельная таблица: это состояние одного диалога в
одном браузере, не то, что должно пережить рестарт сервера.

`require_stepup` (`deps.py`) потребляет challenge ровно один раз — по
заголовку `X-Helm-StepUp`, при самой записи. Свежесть и однократность —
короткий TTL (60с, `settings.stepup_challenge_ttl_seconds`) плюс
привязка к `session_id`, не двойное потребление одного поля.

Модель данных: `PanelSession`, `WebauthnCredential` (§7.2: приватный
ключ никогда не попадает на сервер — только public key),
`PanelEnrollmentToken` (только для первого enrollment),
`PanelStepUpChallenge` (без этой таблицы assertion, полученная для
одного действия, подошла бы к любому другому).

Secondary-пользователь (`KNOWLEDGE_USER`, P8.6.5) входит отдельным
enrollment-токеном, одним фактором против двух факторов владельца —
решение владельца 30.08.2026.

## Не в объёме этого захода

- Возврат к OIDC, если Telegram раскатит его на этого бота — серверная
  часть готова принять это без переделки, реализация не начата, пока
  не нужна.
- Полноценный UI управления сессиями/устройствами в Panel (отозвать
  конкретный passkey и т.п.) — не входит в этот заход.
