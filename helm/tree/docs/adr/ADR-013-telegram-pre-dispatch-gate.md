# ADR-013. Telegram pre-dispatch Control Plane gate

**Дата:** 31.08.2026 · **Статус:** реализовано, задеплоено, живьём
подтверждено (`ROADMAP-TO-DONE.md` п.1.10: счётчик `mode=C1` вырос 0→2
на двух реальных вопросах владельца).

## Контекст

§9.3 (A-DoD п.2-3) требует: ни одно входящее сообщение не должно дойти
до LLM, пока Control Plane не подтвердил его регистрацию.

## Решение

**Fail-closed по конструкции, не по дополнительной проверке.**

`hermes/plugins/helm-control/__init__.py` (докстринг, дословно): «
`pre_gateway_dispatch` регистрирует входящее сообщение в Control Plane
ДО того, как оно дойдёт до LLM. Если Control Plane не подтверждает
регистрацию (недоступен, отверг подпись, отверг owner_id) — сообщение
до модели не доходит: это fail-closed по конструкции, не по доп.
проверке, потому что LLM вызывается уже ПОСЛЕ этой функции, а не внутри
неё.» Формулировка важна: гарантия — в порядке вызовов, не в условии,
которое можно забыть проверить.

`_on_pre_gateway_dispatch()` вызывает `_register_task()` (HMAC-
подписанный `POST /internal/inbound`); любой сбой возвращает
`{"action": "skip", ...}`, уведомляет владельца, сообщение не доходит
до chief. Только на успехе выполнение проваливается дальше — к
Knowledge Probe (§14.11, fail-OPEN, отдельный, более мягкий гейт, не
путать с этим) и, если локального ответа нет, к самой модели.

Серверная сторона: `api/internal.py::/internal/inbound` — за
`require_service_auth` (HMAC) целиком, проверяет `owner_id`, `403`
через `NotOwner` при несовпадении.

### Найденный вживую почти-провал

Плагин изначально лежал под `~/.hermes/hooks/<name>/` — другим,
fire-and-forget механизмом уведомлений — и молча не гейтил ничего, пока
не переехал в правильный opt-in путь `PluginManager`
(`~/.hermes/plugins/<name>/`). Стоит держать в истории этого решения:
гейт, который просто не подключён правильно, неотличим по логам от
работающего гейта, пока не пришёл реальный вопрос, требующий рассуждения.
