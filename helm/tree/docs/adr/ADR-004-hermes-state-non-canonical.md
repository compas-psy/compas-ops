# ADR-004. Hermes state/Kanban non-canonical

**Дата:** 31.08.2026 · **Статус:** принцип реализован и живьём
подтверждён, но нигде не сформулирован одним документом до этого —
здесь ЯВНО помечено, что текст ниже синтезирует решение из нескольких
разрозненных мест, а не цитирует один источник, который сказал бы это
дословно.

## Контекст

У Hermes есть собственное локальное состояние на диске
(`/home/helm/.hermes/kanban.db`, `state.db`) — доска задач и общее
состояние гейтвея. Вопрос: считается ли это состояние источником
правды для Control Plane, или Control Plane обязан иметь собственную,
не зависящую от Hermes систему учёта.

**Важная оговорка перед решением:** в кодовой базе есть ДВЕ разные вещи
с именем «kanban», их нельзя путать:

1. **Настоящий Hermes kanban.db** — файл на диске, упомянут только в
   `scripts/backup.sh` (сырой `.backup`-снимок для disaster recovery) и
   `WORKPLAN.md` («P5 backup покрывает только: состояние/профили/kanban
   Hermes»). Ни один код Control Plane не читает, не запрашивает и не
   доверяет этому файлу ни для одного решения.
2. **`kanban_snapshot`** в `helm_core/actions/fixtures.py`/`config/
   policies/actions.yaml` — тестовая fixture-действие (YELLOW trust) для
   упражнения механики action registry, не реальная фича: «до P4/P7 у
   HELM ещё нет ни канала публикации, ни Kanban». Это имя для примера, а
   не решение об архитектуре доски задач.

## Решение

**Hermes-состояние резервируется как данные Hermes, но никогда не
трактуется Control Plane как источник правды.**

`hermes/plugins/helm-control/__init__.py::_task_ids` — кэш живёт только
в памяти процесса гейтвея, докстринг: «переживает один запуск, не
рестарт» — Hermes-side состояние явно эфемерно и не авторитетно по
конструкции, не по забывчивости.

ADR-012 (durable execution) и approval state machine делают Postgres
Control Plane единственным durable источником правды о том, какие
действия реально произошли — не файлы на стороне Hermes.

`backup.sh` резервирует `kanban.db`/`state.db` целиком (сырой
`.backup`) ровно как defensive-меру («чтобы переустановка Hermes не
потеряла его собственное локальное состояние задач»), а не потому, что
кто-то читает эти файлы для принятия решений.

### Честно о происхождении этого решения

Ни один найденный документ не говорит фразой «kanban.db Hermes —
намеренно не canonical». Вывод собран из трёх независимых мест
(докстринг `_task_ids`, ADR-012, `backup.sh`), которые вместе
последовательно ведут к одному выводу — не из одной прямой цитаты. Если
впоследствии найдётся явное владельческое решение на этот счёт —
обновить этот ADR ссылкой на него, а не оставлять синтез единственным
основанием бессрочно.

## Не в объёме этого захода

- Механизм обнаружения рассинхрона между Hermes-локальным состоянием и
  Control Plane (см. ту же оговорку в ADR-001) — не реализован.
