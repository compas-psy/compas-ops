# ADR-010. Graduated trust

**Дата:** 31.08.2026 · **Статус:** частично реализовано — схема,
инварианты и закрытый список исключений сделаны и защищены на уровне
БД; сам живой цикл повышения доверия НЕ подключён к боевому пути
диспетчеризации.

## Контекст

Спека (D6, `PLAN_HELM_v3.3.md`): «graduated trust — не раньше 10
supervised successes» — уровень требуемого approval для действия должен
иметь возможность понижаться по мере накопленной истории успешных
supervised-запусков, но не для всех действий и не автоматически без
владельца.

## Решение

**Данные и инварианты — в БД, принудительно, не по соглашению кода.**

`ActionTrust` (`models/tables.py`): `current_level`, `supervised_
success` (CHECK `>= 0`), `last_incident_at`, `promoted_at`,
`promoted_by`. CHECK-ограничение `promotion_requires_owner`:
`(promoted_at IS NULL) OR (promoted_by IS NOT NULL)` — повышение
доверия без привязанного владельца невозможно физически, не только по
проверке в коде (протестировано против настоящего Postgres именно
из-за этого CHECK, не SQLite).

`policy.py::NEVER_GRADUATE` — закрытый список, зашитый в код, не
редактируемый через policy-YAML: `spend_money`, `legal_submission`,
`delete_business_data`, `change_price`, `signalai_live_execution`,
`secret_rotation`, `change_policy`, `change_trust_level` никогда не
понижаются ниже начального RED-уровня, сколько бы успешных запусков ни
накопилось. Комментарий рядом объясняет асимметрию сознательно:
policy-файл редактируется агентом по одобрению, а этот инвариант — нет.

`check_demotion()` — `minimum_allowed_level` как пол для всех
остальных действий; порог «10 supervised successes» из спеки
зашит и в Panel (`api/panel.py`, `"threshold": 10` на эндпоинте деталей
approval) для отображения человеку-ревьюеру.

### Не в объёме этого захода — живой цикл не подключён

Боевой путь предложения действия — `ApprovalService.propose()` —
всегда использует `spec.initial_level`, никогда не читает `ActionTrust`
и не вычисляет `effective_level`. `execute_direct(effective_level=...)`
нигде в прикладном коде не вызывается с непустым `effective_level` —
только тесты создают строки `ActionTrust` напрямую. Ничто не
инкрементирует `supervised_success` автоматически, и нет
мутирующего эндпоинта, который бы явно повышал `current_level`. Panel
сегодня ТОЛЬКО показывает `ActionTrust`, не пишет в неё.

Это тот же класс находки, что уже стоил живого урока `approvals/
service.py` (докстринг: живой смоук-тест обнаружил, что
`execute_direct()` было решительно неоткуда вызывать — ни один HTTP-
маршрут его не вызывал) — механизм построен и защищён на уровне схемы,
но реальная петля обратной связи ("накопил успехи → владелец
пересмотрел → следующие запуски идут по пониженному уровню") ещё не
собрана в один путь.

## Не в объёме этого захода

- Автоматический подсчёт `supervised_success` по факту успешного
  выполнения действия.
- Эндпоинт/UI-действие, которым владелец реально повышает
  `current_level` (Panel сегодня только читает).
- Подключение `effective_level` к `ApprovalService.propose()`.
