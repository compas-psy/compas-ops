# ADR-031. Per-user fair queue/quotas/style isolation

**Дата:** 31.08.2026 · **Статус:** реализовано и задеплоено v3.8 Фаза 2,
подтверждено тестами (`test_knowledge_quotas.py`,
`test_claim_next_job_is_fair_round_robin_across_tenants`).

## Контекст

§14.4 формулирует единственную runtime-опасность многопользовательского
Second Brain на 12 GB VPS буквально: "one user must not starve others or
kill the box". Без per-user лимитов один загруженный ZIP-архив одного
KNOWLEDGE_USER мог бы занять всю очередь разбора и весь диск, оставив
остальных (включая владельца) без обслуживания.

## Решение

Три независимых механизма закрывают три разных способа "съесть общий
ресурс" — не один общий "лимит", потому что byte-квота, глубина очереди
и порядок обслуживания ловят разные сценарии злоупотребления.

### Байтовые квоты — `quotas.py`

`check_and_record_ingest()` — `storage_quota_bytes`/
`daily_ingest_quota_bytes` на `KnowledgeUser`, `None` = без ограничения
(backfill v3.8 не проставил лимитов владельцу). Проверка ДО записи
файла (§14.4 "oversized user upload rejected before resource
exhaustion"), не постфактум — и увеличение счётчика неразделимо с
проверкой в одном вызове, иначе конкурентные загрузки могли бы обе
пройти проверку до того, как любая из них учтётся. Дневной счётчик —
ленивый сброс "по факту" при первом обращении в новый календарный день
(UTC), не отдельная cron-задача на полночь.

Осознанно упрощено: `KnowledgeUserUsage.storage_bytes` монотонно
растёт — отключение/архивирование source квоту не освобождает. Полный
учёт "свободного места после удаления" — отдельная, не начатая задача;
цель этого механизма — не дать разово залить сервер сверх лимита, не
точный биллинг.

### Глубина очереди — `check_queue_depth()`

`MAX_QUEUED_JOBS_PER_USER = 50` — глобальная константа, не колонка
`KnowledgeUser`: начинаем с простого явного предела, не вводим ещё одно
квотируемое поле в схему, пока не появился конкретный повод сделать его
настраиваемым per-user. Проверяется при получении файла/архива, до
постановки job'а — не после, чтобы не создавать сотни
`KnowledgeIngestJob`, из которых половина потом откатывается. Explicit-
предикат в коде здесь же, что и в RLS (ADR-030) — оба слоя, ни один не
заменяет другой.

### Fair round-robin — `worker.py::claim_next_job()`

Один воркер, одна очередь `knowledge_ingest_jobs` под RLS — единственный
способ увидеть работу больше чем одного тенанта без отдельной
service-роли с `BYPASSRLS` (спека разрешает, но заводить вторую БД-роль
ради этого — инфраструктура без надобности). `claim_next_job()`
перебирает активных тенантов по кругу (`_last_served_tenant_index`),
привязывая RLS-сессию к каждому по очереди, и берёт первый, у которого
вообще есть `PENDING` работа — "one user's large ZIP does not starve
another user's short upload" в буквальном смысле: большой бэклог одного
тенанта не откладывает единственный job другого до полного исчерпания
первого. Для сегодняшнего единственного активного тенанта (SYSTEM_OWNER)
поведение не отличается от прежнего чистого FIFO.

`_last_served_voice_tenant_index` (ADR-021 фаза 2b) — отдельный индекс
для voice-pending, не общий с document-job'ами: две разные очереди,
round-robin по одной не должен влиять на другую. Оба индекса —
модульное состояние процесса, не персистентное: справедливость нужна на
время жизни воркера, не через рестарт (после рестарта распределение
стартует заново — не портит гарантию "ни один тенант не голодает
бесконечно").

### Стиль — per-user изоляция тем же двойным гейтом, что и роль

`style.py`/`rephrase.py` — персональный стиль владельца применяется
только при `style_profile_version` СОВПАДАЕТ с текущим `OWNER_STYLE_
VERSION` И `role == SYSTEM_OWNER` (см. ADR-028). Второй KNOWLEDGE_USER
с тем же номером версии не получает чужой стиль по случайному
совпадению числа; собственный стиль для KNOWLEDGE_USER (P8.6.6) —
разобран отдельно и не реализуется в этом заходе (нет ступени синтеза
профиля из переписки, см. `V3.8-ACCEPTANCE.md`).

## Не в объёме этого захода

- Настраиваемая per-user глубина очереди (сегодня — одна глобальная
  константа на всех тенантов).
- Освобождение storage-квоты при удалении/архивировании source.
- Собственный стиль для KNOWLEDGE_USER (P8.6.6, нет ступени синтеза).
