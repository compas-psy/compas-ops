# TROUBLESHOOTING — реальные классы багов, найденные живьём

Не гипотетический чек-лист — каждый пункт ниже случился на этом сервере
и задокументирован в `STATUS.json::open_findings`/`resolved_this_cycle`
с точным ID (`F-YYMMDD-NN`) для полного разбора. Сгруппировано по
симптому, не по хронологии — цель: узнать симптом быстрее, чем читать
все 45+ находок по порядку.

## «502 Bad Gateway» от внутреннего Docker-сервиса

**Симптом**: `helm-core` не может достучаться до соседнего контейнера
в той же bridge-сети (`helm-embed`, `ollama`), хотя контейнер сам
здоров.

**Причина**: `helm-core` несёт `HTTP_PROXY`/`HTTPS_PROXY` для похода в
OpenRouter через `sing-box`-туннель (VPS заблокирован OpenRouter по
IP/датацентру). `urllib.request` читает эти переменные окружения и
заворачивает ЛЮБОЙ HTTP-запрос через туннель, включая внутренний
Docker-DNS вызов — туннель это имя не резолвит, 502 приходит от
прокси, не от самого сервиса.

**Фикс**: добавить имя нового внутреннего сервиса в `NO_PROXY` в
`docker-compose.yml`. Случилось дважды (F-260831-02 для `helm-embed`,
F-260831-05 для `ollama`) — **при заведении ЛЮБОГО нового внутреннего
сервиса, к которому обращается `helm-core`, проверить `NO_PROXY`
первым делом**, не постфактум после первого живого 502.

## Деплой зависает на «Доставка файлов» (`scp -r`)

**Симптом**: шаг деплоя висит 8+ минут без прогресса на передаче
единиц мегабайт (`helm_core`+`migrations`+`panel/dist`).

**Причина**: `scp -r` в OpenSSH 9.x по умолчанию идёт через SFTP-
подсистему, не старый SCP-протокол — задокументированный класс
зависаний именно на рекурсивной передаче дерева из многих мелких
файлов (F-260831-07).

**Фикс** (уже внедрён в `deploy.yml`): staging файлов в один временный
каталог + один `tar czf | ssh exec 'tar xzf'`. НЕ архивировать `.` как
запись (только явный список путей) — `tar -C dir .` при извлечении в
`/tmp` пытается restore владельца/прав на сам `/tmp` (root, sticky bit),
non-root пользователь получает `Operation not permitted`.

**Смежный урок**: после уборки Docker build cache следующий `docker
compose build` неизбежно идёт с нуля и может занять 40-70 минут вместо
обычных ~2 — это НЕ зависание. Судить о зависшем шаге по одному
прошедшему времени нельзя — смотреть реальный лог на прогресс
(скачивание идёт, шаг сборки продвигается) перед отменой.

## `Invalid cross-device link` на `os.replace()`

**Симптом**: `OSError: [Errno 18]` при перемещении файла между двумя
каталогами, которые "должны быть на одном диске".

**Причина**: два каталога под общим родителем (`/opt/X`, `/opt/Y`) не
гарантированно на одной точке монтирования просто потому, что лежат
рядом (F-260829-33: `helm-state/knowledge-spool` и `helm-knowledge`
оказались разными ФС). Атомарный `rename` между файловыми системами
невозможен на уровне ядра, не чинится правами.

**Фикс**: copy во временный файл НА ЦЕЛЕВОЙ файловой системе + `os.
replace()` внутри неё (гарантированно один диск) + удаление исходника
только после успеха. Общее правило: для любой операции, которой нужна
атомарность между двумя КОНФИГУРИРУЕМЫМИ путями — не полагаться на
«наверное один диск», писать copy-to-tmp-on-destination+rename сразу.

## Секрет «не найден» при заведении нового

**Симптом**: `read_secret()` падает `RuntimeError`, хотя файл вроде бы
создан.

**Частые причины**: (1) файл создан по пути ХОСТА
(`/etc/helm/secrets/...`), а `read_secret()` внутри контейнера читает
`/run/secrets/...` (Docker secrets mount point) — это два разных пути,
`docker-compose.yml` монтирует первый во второй; (2) неверные права —
де-факто конвенция `root:root 0600` для секретов, которые читает только
host-скрипт, `root:helm-secrets 0640` для монтируемых в контейнер
(группе принадлежит процесс Docker). Сверяться с `ls -la
/etc/helm/secrets/` на уже рабочих записях перед созданием нового, не
угадывать по общей интуиции. Полный список — `SECRETS_MAP.md`.

## `psql -v name=value` + `:'name'` не подставляется

**Симптом**: `syntax error at or near ":"` в SQL, где ожидалась
подстановка переменной.

**Причина**: `:'name'`-подстановка psql работает только при передаче
SQL через **stdin**, не через `-c "..."` — в `-c` это просто
синтаксическая ошибка (F-260829-06, и тот же класс бага пойман заново
внутри `\047`-квотинга SSH-команды в `deploy.yml`::verify).

**Фикс**: передавать SQL через stdin (heredoc или pipe), не `-c`. Для
экранирования одинарной кавычки внутри уже одинарно-квотированной
bash-команды — стандартный приём `'"'"'`, не `\047` (октальный escape
внутри одинарных кавычек bash не интерпретируется).

## Bind-адрес недоступен снаружи контейнера

**Симптом**: сервис внутри контейнера отвечает на `localhost`, но
недоступен через docker-сеть/прокси.

**Причина**: сервис слушает `127.0.0.1` ВНУТРИ контейнера — это
loopback контейнера, не хоста; снаружи (даже из другого контейнера той
же docker-сети) недоступим. Повторялось дважды (`helm-core` на P2,
n8n — F-260829-14): нужен bind на `0.0.0.0` (или явный интерфейс
контейнера) внутри, а публичный доступ ограничивается на уровне Caddy/
firewall, не на уровне bind-адреса приложения.

## MAX-канал — набор специфичных, не Telegram-подобных проблем

- Секрет вебхука не должен содержать `/`/`+` (base64-алфавит) — MAX Bot
  API отвергает `HTTP 400` (F-260829-20).
- Ответ по `chat_id` из РЕАЛЬНОГО вебхука, не из id отправителя —
  «Unknown recipient» иначе (F-260829-21).
- Id владельца в MAX — другое число, чем Telegram-id, мессенджеры не
  делят пространство id (F-260829-17).
- `platform-api2.max.ru` отдаёт сертификат от «Russian Trusted Sub CA»
  (Минцифры) — этого корня нет в стандартном наборе Debian/Ubuntu,
  нужен отдельный шаг доверия (F-260829-19).

## Caddy отдаёт 404 на всё после `rm -rf` примонтированного каталога

**Причина**: bind-mount на хостовую директорию «протухает» после того,
как сама директория удалена и пересоздана под тем же именем — Caddy
держит старый inode (F-260829-10).

**Фикс**: содержимое каталога заменяется (`rm -rf панель/dist/*` +
копирование новых файлов ВНУТРЬ), сам каталог никогда не удаляется и
не пересоздаётся — тот же принцип уже применён в `deploy.yml`
(«Разложить и пересобрать»).

## Сборка образа: torch/torchvision/docling/pydantic

Пакеты, устанавливаемые в отдельных `RUN pip install` шагах Dockerfile,
могут конфликтовать по ABI/версии, если порядок или источник (`--index-
url`) не совпадают между связанными пакетами (F-260829-28 torch/
torchvision, F-260829-29 docling-core/pydantic ordering). Держать список
зависимостей в ОДНОМ месте (`pyproject.toml`), не дублировать вручную в
Dockerfile (сам этот дубль — отдельная находка, F-260829-08).

## Права между контейнерами на общий volume

UID контейнера-писателя (например, `helm-knowledge-worker`, UID 10002)
должен совпадать или иметь права на каталог, созданный ДРУГИМ
процессом с другим UID (хостовый `helm`, UID 1000) — иначе
`PermissionError` на каждой попытке записи (F-260829-31).

## Две системы хуков Hermes с похожими именами

`~/.hermes/hooks/<name>/` (fire-and-forget уведомления) и
`~/.hermes/plugins/<name>/` (реальный `PluginManager`, единственный
путь, который может ГЕЙТИТЬ диспетч) — визуально похожи, семантически
разные (F-260829-02). Плагин в неправильном каталоге молча не гейтит
ничего, не выдаёт ошибки — см. живой почти-провал в ADR-013.

## Официальный образ Postgres стартует дважды на первом запуске

`docker logs` покажет «database system is ready to accept connections»
ДВАЖДЫ — первый раз от временного сервера (только для init-скриптов),
второй — от финального. `pg_isready` может успеть ответить «готов» для
временного сервера прямо перед тем, как он погаснет — гонка. Ждать
именно ВТОРОЕ вхождение строки в логе, не одноразовый `pg_isready`
(`restore_test.sh`, найдено 29.08.2026).

## Бот молчит: sing-box не стартует из-за висячей ссылки в конфиге

Найдено живьём 06.09.2026, прогоны 334–336.

Этот сервер не достаёт до Telegram напрямую: весь трафик бота идёт через
`sing-box@openrouter-proxy.service` (слушатель `0.0.0.0:18080`). Когда
умер upstream `mieru-out`, туннель переключили на hysteria2 — убрали
мёртвый outbound и поставили новый. Служба после этого ушла в цикл
падений:

```
FATAL start service: start dns/udp[remote]: outbound detour not found: mieru-out
```

На убранный outbound ссылался `detour` у DNS-сервера. Порт 18080 не
слушался вовсе, `curl` через прокси отвечал `(7) Couldn't connect`, а
шлюз — `httpx.ConnectError: All connection attempts failed`. Симптом
выглядит как «туннель не работает», причина — «конфиг не грузится».

Три вывода, каждый оплачен прогоном:

1. **`sing-box check` этого НЕ ловит.** Он разбирает схему; висячий
   `detour` вскрывается только при старте службы. Проверять надо после
   рестарта: счётчик `NRestarts` не вырос за десяток секунд, `is-active`
   = `active`, порт слушается. Одного `is-active` мало — в цикле падений
   systemd успевает отвечать `active` между стартом и падением.
2. **Убирая outbound, перенацеливай все ссылки на него** —
   `dns.servers[].detour` и `route.rules[].outbound`. Проверять надо не
   «ссылки на убранный тег», а любую ссылку на несуществующий тег: после
   неудачной правки висячая ссылка ведёт уже не на тот тег, который
   убираешь сейчас.
3. **Проверка связности должна ловить провал.**
   `code=$(curl -w '%{http_code}' … || echo 000)` — ловушка: при провале
   curl сам печатает `000` через `-w`, запасное `echo` дописывает
   второй, получается `000\n000`, что не равно `000`. Гейт становится
   бумажным и объявляет успех на мёртвом туннеле.

Диагностика: `scripts/tunnel-hysteria2-diag.sh` (только чтение).

## sing-box 1.14 уронит туннель: в конфиге устаревший формат DNS

Найдено 06.09.2026, прогон 339, проверено живым `sing-box check` 1.13.19.

`/etc/sing-box/openrouter-proxy.json` описывает DNS-серверы в старой
форме (`{"tag", "address", "detour"}`). Ядро 1.13.19 её уже не принимает
само по себе:

```
ERROR legacy DNS servers is deprecated in sing-box 1.12.0 and will be
      removed in sing-box 1.14.0
FATAL to continuing using this feature, set environment variable
      ENABLE_DEPRECATED_LEGACY_DNS_SERVERS=true
```

Служба работает только потому, что этот флаг где-то выставлен. **Любое
обновление до 1.14 остановит туннель и бот замолчит ровно так же, как
06.09.2026.** Мигрировать надо на форму `{"tag", "type": "udp",
"server": "…", "detour": …}` — она принимается 1.13.19 (проверено).

Заодно проверено на том же ядре: `inbound.sniff: true` **удалён** в
1.13.0 (FATAL), вместо него правило маршрута `{"action": "sniff"}` —
принимается.
