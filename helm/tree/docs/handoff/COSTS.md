# COSTS — сколько тратится на платные модели и как это ограничено

Единственная статья расхода на платные модели — OpenRouter через
LiteLLM (`MODEL_ROUTING.md`). Все локальные модели (embeddings, GigaAM,
Ollama Z2) — бесплатны, `paid_ai_used=False` по построению.

## Как посмотреть текущий расход

`scripts/check_spend.sh` — читает `LiteLLM_SpendLogs` напрямую из БД
`litellm` (отдельная БД от `helm`, см. `SECRETS_MAP.md`):

```bash
sudo bash /opt/helm/scripts/check_spend.sh
```

Выводит расход по каждой модели (`model, calls, total_spend`) и итог.

## Дневные бюджетные потолки — per-profile, не общий

`scripts/set_key_budgets.sh` — владельческое решение 29.08.2026, после
проверки реального spend перед Milestone B: каждый LiteLLM virtual key
профиля Hermes (`default`, `business`, `engineering`, `health`,
`reviewer`) получает свой дневной потолок (`max_budget`, по умолчанию
$5, `budget_duration=24h`) — чтобы баг или зацикливание одного профиля
не могли сжечь бюджет бесконтрольно, и чтобы это не било по остальным
профилям.

```bash
sudo bash /opt/helm/scripts/set_key_budgets.sh [дневной_лимит_в_долларах]
```

Вывод скрипта намеренно не печатает сырой ответ API целиком — LiteLLM
эхом возвращает сам ключ в теле ответа, скрипт печатает только
безопасные поля (`max_budget`, `budget_duration`, `key_alias`).

## Метрика в самом продукте — `paid_ai_used` (§14.14)

`KnowledgeAnswerRun.paid_ai_used` — булево на каждый ответ Knowledge:
`False` для Z0/Z1/Z2 (локальные), `True` только на реальную эскалацию к
Hermes через `/hooks/max`/`api/internal.py`. Это не биллинг-метрика в
долларах, а счётчик "сколько раз вообще пришлось заплатить" — считает
входы, спека рассматривает это как показатель эффективности
бесплатного пути (чем реже `paid_ai_used=True`, тем лучше отрабатывает
Probe), не как контроль расходов напрямую.

## Что этот документ не покрывает

- Исторический график расходов/дашборд — не строится (ADR-011, нет
  тяжёлого стека мониторинга); `check_spend.sh` — снимок на момент
  запуска, не временной ряд.
- Оповещение при приближении к бюджетному потолку — LiteLLM просто
  отклоняет запрос сверх `max_budget`, отдельного алерта владельцу об
  этом нет (не покрыто Guardian — Guardian следит за диском/RAM, не за
  расходом).
