# OPERATIONS — повседневная эксплуатация

Единственный способ агента работать с живым сервером — `.github/
workflows/deploy.yml` (`workflow_dispatch`, репозиторий
`compas-psy/compas-ops`). Приватный ключ отдельной SSH-пары лежит в
GitHub Secrets, агент запускает workflow и читает логи, самого ключа не
видит никогда (CLAUDE.md §5.4, устав §6). Действия — только через
явный выбор, дефолт `verify` (read-only), случайный запуск ничего не
меняет.

## Действия deploy.yml

| Действие | Что делает | Когда использовать |
|---|---|---|
| `verify` | Контейнеры, ревизия схемы, роль БД, объём знаний, диск/память, дата бэкапа — только чтение | Первым делом на любой вопрос "что там сейчас" |
| `keyscan` | Печатает `ssh-keyscan` сервера для `VPS_KNOWN_HOSTS` | Только при первой настройке или ротации ключа |
| `backup` | `backup.sh` на сервере | Перед рискованным изменением |
| `deploy` | Сборка панели (npm), доставка файлов (tar через ssh exec, не `scp -r` — см. `TROUBLESHOOTING.md`), пересборка `helm-core`/`helm-knowledge-worker`, поднятие `ollama` + pull модели, рестарт caddy/hermes-gateway | Выкат нового кода |
| `migrate` | `alembic upgrade head`, ПОСЛЕ deploy, отдельным шагом | После деплоя, если есть новая миграция |
| `recon` | Доставляет и запускает один файл из `scripts/*.sh` (параметр `script`) | Разовая живая проверка/разведка, ничего не оставляет на сервере |
| `restore-test` | `backup.sh` + `restore_test.sh` | Периодическая проверка, что бэкап реально восстановим |
| `rollback` | `alembic downgrade` до указанной ревизии (параметр `revision`) | Откат схемы после неудачной миграции |

`concurrency: group: deploy, cancel-in-progress: false` — деплой и
recon никогда не идут параллельно друг с другом (ночной цикл — другая
группа, `rhythm`, не конкурирует с этой).

## Как читать `verify`

```
=== контейнеры ===          — docker compose ps, все ли healthy
=== ревизия схемы ===       — alembic current, сверить с HEAD миграций
=== роль базы ===           — helm_app: rolsuper=f (ожидается, НЕ t)
=== объём знаний ===        — count(*) knowledge_sources
=== место и память ===      — df -h /, free -h
=== последний бэкап ===     — mtime /var/lib/helm-guardian/last-backup
```

Если `rolsuper=t` для `helm_app` — критическая находка: RLS-изоляция
(ADR-030) декоративна, суперпользователь обходит любую политику.

## Типичная последовательность для нового кода

1. `verify` — убедиться, что сервер здоров ДО начала.
2. `deploy` — выкатить код (миграции НЕ применяются этим шагом).
3. Если есть новая миграция — `migrate` отдельным вызовом, сверить
   "было"/"стало" в логе шага.
4. `recon` с нужным скриптом — живая функциональная проверка новой
   фичи в откатываемой транзакции (шаблон — `scripts/verify-*.sh`).
5. `verify` ещё раз — контейнеры healthy, ничего не сломалось.

## Guardian — что он делает и на что реагирует

Независимый watchdog (systemd-таймер, каждые 5 минут), stdlib-only,
живёт независимо от Docker/Postgres/Control Plane/Hermes — обязан
сообщить именно об ИХ падении (ADR-011, §30.10). Пороги — устойчивое
15-минутное окно, не мгновенный пик: диск `70/82/90%`
(warn/critical/emergency), RAM `75/88%`. Алерты уходят владельцу
напрямую в Telegram, минуя Control Plane/Hermes. Guardian никогда не
принимает команд и не исполняет действий (§25.5) — чисто наблюдатель.

Состояние: `/var/lib/helm-guardian/public-status.json` (то же самое,
что видит Panel-таблица ресурсов), `alerts.jsonl`, `metrics.jsonl`,
`last-backup`/`last-restore-test` (mtime-метки).

## Диагностика зависшего/медленного деплоя

**Не судить по одному прошедшему времени.** После уборки Docker build
cache следующая сборка неизбежно идёт с нуля (40-70 минут вместо ~2) —
это не баг. Смотреть реальный лог шага (`get_job_logs` в терминах
GitHub Actions) на признаки прогресса: скачивание идёт с ненулевой
скоростью, шаг сборки продвигается — прежде чем отменять запуск (живой
урок, `TROUBLESHOOTING.md`).

## Расход диска

`docker builder prune -af` безопасен для промежуточных build-слоёв
(не runtime-образы) — накапливается за много деплоев. `docker system
df -v` — снимок перед решением, что чистить. Не трогать docker volumes
(данные) и старые ядра без отдельного решения.

## Контроль расходов на платные модели

`scripts/check_spend.sh` (снимок), `scripts/set_key_budgets.sh`
(дневные потолки per-profile) — подробности `COSTS.md`.

## Восстановление доступа к Panel

`scripts/panel-passkey-recover.py` на самом сервере, root — подробности
`PANEL_AUTH_RECOVERY.md`.

## Что этот документ не покрывает

- Пошаговое аварийное восстановление сервера с нуля (не тестовое
  восстановление, а реальный disaster recovery) — `restore_test.sh`
  проверяет ТОЛЬКО что бэкап валиден, не разворачивает прод; отдельный
  ранбук для этого не написан (см. `BACKUP_RESTORE.md`, последний
  раздел).
- Масштабирование/увеличение сервера — решение владельца, не
  автоматизировано (D5, `ROADMAP-TO-DONE.md` блок 4).
