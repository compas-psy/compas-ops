# SIGNALAI_MIGRATION — не начато, спека прямо запрещает начинать раньше

**Статус: не начато, гейт (не дизайн) — единственное, что решено.**

## Что решено

`ROADMAP-TO-DONE.md` (Блок 4, «Веха D»):

> `D — SignalAI | Переезд на этот же VPS | Не начата, по ТЗ раньше
> нельзя`

> `7 дней метрик после C | Прямое требование: до этого D не начинать`
> `P13 SignalAI | Переезд на этот же VPS только после PASS по A–C, семи
> дней метрик и отсутствия устойчивой нехватки ресурсов. Решение об
> увеличении сервера — за владельцем, автоматически не наращивается
> (D5)`

Единственный реально принятый «дизайн» — это условие входа: Milestone
D (перенос SignalAI) не начинается, пока не пройдены A-C ЦЕЛИКОМ, не
накоплено 7 дней чистых метрик после этого, и нет устойчивой нехватки
ресурсов на сервере. Решение о необходимости увеличить сервер —
владельца, не автоматическое (D5).

## Чего не решено вовсе

Архитектуры «single-writer» (тема §34/007) не существует ни в каком
виде — ни схемы, ни выбора, кто именно будет single writer, ни
изоляции ресурсов между SignalAI и HELM на одном VPS. Ни строки кода,
ни упоминания SignalAI нигде в `helm/tree` кроме этого документа и
`ROADMAP-TO-DONE.md`.

## Почему ADR-007 честно не написан

Milestone C (домены) сама «не начата» — до неё дело ещё не дошло, D
идёт следом. Писать ADR о «решении», которого физически нет — значило
бы выдать пустоту за архитектуру (`docs/adr/README.md` фиксирует этот
же честный случай явно, рядом с `002` n8n adapter boundary).

## Что нужно сделать перед тем, как это начинать

1. Дождаться PASS по Milestone C целиком (`ROADMAP-TO-DONE.md`, блок 3).
2. 7 дней метрик без инцидентов после этого.
3. Проверить фактическую нехватку ресурсов на сервере — если она
   устойчива, решение об увеличении сервера — отдельный шаг владельца
   (не эта миграция).
4. Только тогда начинать проектирование single-writer архитектуры —
   с нуля, не по этому документу, в котором пока нечего описывать.
