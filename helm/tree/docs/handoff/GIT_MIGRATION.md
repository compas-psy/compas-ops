# GIT_MIGRATION — переезд с GitHub на Forgejo как primary

Целевая архитектура — ADR-006 (Forgejo primary, GitHub push-mirror+CI).
Этот документ — состояние самой миграции: план готов, **выполнение не
начато** (`MIGRATION-LOG.md`, §18.3).

## Статус по шагам

Шаг 1 (инвентаризация) — выполнен 29.08.2026, удалённо, blobless sparse
clone (только refs + `.github/`, без полных клонов). Шаги 2-9
(`scripts/forgejo-migrate.py`, ранбук `scripts/forgejo-migrate-runbook.
md`), шаг 10 (доказать CI на зеркале) и шаг 11 (переключение primary
remote) — **не выполнены**, каждый требует отдельного решения владельца
по репозиторию.

## Четыре находки, каждая — открытое решение владельца (не блокер)

1. **`zapiski` и `signalAI-mobileApp` — default branch не `main`.**
   Миграция перенесёт как есть. У `zapiski` половина workflow
   триггерится именно на эту ветку — она реально рабочая, не забытая.
   Решение (оставить/привести к `main`) нужно до шага 11, не раньше.
2. **309 веток в `signalAI-mobileApp`.** Push-mirror перенесёт и вернёт
   все без расхождений технически — вопрос только нужна ли эта история
   в новом primary. Чистка дешевле ДО миграции, чем после (после —
   удалять в двух местах).
3. **GitHub Issues — рабочая командная панель `signalAI-mobileApp`.**
   Шесть workflow триггерятся на `issue_comment`/`workflow_run`
   (`owner-commands.yml` и т.д.) — GitHub для этого репозитория не
   только зеркало кода. §18.3: «PR metadata и issue-комментарии
   автоматически не зеркалятся». После переключения primary эти команды
   продолжат работать ТОЛЬКО на GitHub-стороне — принять сознательно
   или перенести механизм. Практический вывод: `signalAI-mobileApp`
   мигрировать последним, отдельным решением.
4. **Push-workflow привязаны к `main`/тегам — не к произвольной
   ветке.** Безопасно для деплоя (и не должно срабатывать на
   feature-ветках), но означает: сценарий §18.6/§19 «feature branch →
   Forgejo PR → mirrored SHA CI на GitHub → зелёный CI на точном SHA»
   не сработает НИ РАЗУ для этих репозиториев — не потому что упадёт, а
   потому что запускать нечего (среди них нет workflow, реально
   проверяющего код на произвольной ветке, только build/deploy). Это
   отдельная задача Milestone P8 (завести тестовый workflow на любую
   ветку), не блокер самой Git-миграции.

## §18.5 — проверено, обходной путь не нужен

Ни один workflow ни в одном из пяти репозиториев не запускается ТОЛЬКО
на `pull_request` (для которого зеркало не создаёт событие) — «safe
push/manual exact-ref path», который §18.5 разрешает как обходной путь
на такой случай, заводить не потребовалось.

## Порядок миграции

`compas-ops` — **последним**: push mirror перезаписал бы свежие
GitHub-refs текущей рабочей ветки. `signalAI-mobileApp` — тоже
последним, отдельным решением (находка 3 выше). Остальные три
(`compas-voice`, `cmpas.ru`, `zapiski`) не имеют такой блокирующей
находки.

## Что делать следующему, кто продолжит миграцию

1. Прочитать `scripts/forgejo-migrate-runbook.md` целиком.
2. Получить владельческие решения по находкам 1 и 2 (default branch,
   чистка веток) для `zapiski`/`signalAI-mobileApp` — не обязательно
   ДО начала миграции остальных трёх репозиториев.
3. Запустить `forgejo-migrate.py` на первом из трёх «чистых»
   репозиториев, проверить открытые PR в его выводе (§18.3 требует
   сохранить URL/history).
4. После PASS шага 10 (CI на зеркале) — переключение primary remote
   ПО ОДНОМУ репозиторию, отдельным решением владельца на каждый
   (ADR-006).
