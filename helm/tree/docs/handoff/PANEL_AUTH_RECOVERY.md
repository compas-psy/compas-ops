# PANEL_AUTH_RECOVERY — восстановление доступа к Panel при утере passkey

§10.5.8.2. Скрипт: `scripts/panel-passkey-recover.py`, разворачивается
на сервере как `/opt/helm/scripts/panel-passkey-recover`. См. ADR-016
для устройства самой аутентификации (Telegram Login Widget + WebAuthn).

## Когда это нужно

Владелец потерял ВСЕ рабочие passkey (устройство утеряно/сброшено) и не
может пройти обычный passkey-логин в Panel.

## Кто может это запустить

**Только тот, у кого есть root на самом сервере HELM** — единственная
защита скрипта: он пишет напрямую в БД Control Plane через `docker exec
... psql`, минуя API и HMAC-подпись сервисных вызовов. Требует
`/etc/helm/secrets/telegram_owner_id` (падает явной ошибкой, если
секрета нет — "скрипт запускается на самом сервере HELM").

## Что делает, по порядку

1. Показывает список активных passkey владельца (label + дата создания)
   для интерактивного выбора, что отозвать.
2. Отзывает **ВСЕ** активные `panel_sessions` владельца безусловно —
   независимо от того, сколько passkey отзывается.
3. По выбору (интерактивно или флагом `--revoke-all-credentials`)
   отзывает один, несколько или все `webauthn_credentials`.
4. Выпускает новый одноразовый enrollment-токен, TTL 30 минут — в БД
   хранится только его SHA256-хэш, не сам токен.
5. **Печатает токен РОВНО ОДИН РАЗ в терминал** — никогда не пишется в
   лог, файл или Telegram/MAX (§10.5.8.2: "recovery token никогда не
   уходит автоматически"). Тот, кто запускает скрипт, обязан передать
   его владельцу лично, не через мессенджер.
6. Пишет аудиторскую запись (БЕЗ самого токена) в
   `/var/log/helm/panel-recovery.log` (`0600`, создаётся при
   необходимости `0700`): кто запустил (`SUDO_USER`/`USER`), сколько
   сессий/credentials отозвано, что токен выпущен.

## Как владелец завершает восстановление

Открывает `/login?step=enroll` после повторного входа через Telegram
Login Widget, использует полученный токен — та же ветка `register_
options`/`register_verify` в `auth.py`, что и у самого первого
enrollment (ADR-016), не отдельный код.

## Безопасность SQL-слоя

Значения подставляются только через `psql -v name=value` + `:'name'` в
самом SQL-тексте — psql сам безопасно экранирует как SQL-литерал,
ручная склейка строк запрещена. SQL идёт через stdin, не `-c`:
`:'name'`-подстановка в `-c` не работает вовсе (проверено — синтаксическая
ошибка), через stdin — штатно.

## Что этот документ не покрывает

- Восстановление доступа для KNOWLEDGE_USER (secondary Panel-логин,
  P8.6.5) — этот скрипт работает только с `owner_id` из
  `telegram_owner_id`, secondary-пользователей не касается. Отдельного
  recovery-пути для них не найдено — открытый пробел.
