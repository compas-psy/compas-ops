# BACKUP_RESTORE — что бэкапится, как проверяется, как восстановить

Актуально на 02.09.2026 (`scripts/backup.sh`/`restore_test.sh`/
`local-rescue-checkpoint.sh`). Восстановление из offsite проверялось на
реальном снапшоте 31.08.2026.

## Две страховки, и путать их нельзя

| | локальная точка возврата | offsite-бэкап |
|---|---|---|
| скрипт | `local-rescue-checkpoint.sh` | `backup.sh` |
| от чего спасает | ошибка выката | потеря машины |
| где лежит | тот же диск, `/opt/helm-rescue-checkpoints` | Яндекс Диск через restic |
| сколько занимает | десятки секунд | двадцать минут и больше |
| от кого зависит | ни от кого | от стороннего хранилища |
| когда обязательна | перед каждым `deploy`/`migrate` | перед любым необратимым действием |

Локальная копия лежит на том же диске, что и данные. Это осознанный
предел: от отказа диска она не спасает и заменой offsite не является.
Поэтому гейт необратимых действий в `deploy.yml` (удаление данных, purge
файлов, downgrade схемы) её не принимает — ему нужен свежий offsite С
пройденным restore-тестом либо подтверждённый снапшот провайдера.

### Что в локальной точке возврата

`pg_dumpall` целиком (с ролями — они и есть health-изоляция),
`/opt/helm-knowledge` и `/opt/helm-knowledge-private` отдельными
архивами, конфигурация (`compose`, `config`, `scripts`, `guardian`),
отпечатки секретов БЕЗ значений (имена, права, sha256 — CLAUDE.md §5.4;
значения только в offsite-бэкапе), `MANIFEST.txt` с выкаченной ревизией,
ревизией схемы и счётчиками строк, `SHA256SUMS`. Сразу после записи
скрипт сам проверяет суммы и целость архивов: точка возврата, целость
которой не проверили сразу, — обещание, а не страховка.

Держатся три последних; ниже 4 ГБ свободного места скрипт отказывается
начинать. `local-rescue-checkpoint.sh verify` перечитывает последнюю.

## Куда уходит бэкап

`restic` в репозиторий `rclone:yandex:helm-backup` (Яндекс Диск).
Пароль шифрования репозитория — `/etc/helm/secrets/restic_password`
(**единственная копия** — без него снапшоты не расшифровать, см.
`SECRETS_MAP.md`). Запуск — от root, `helm-backup.service`
(systemd, ежедневно).

## Что попадает в снапшот (`--tag helm-daily`)

1. **PostgreSQL** — `pg_dumpall` целиком (все БД + роли), не по одной
   базе — простое решение: не поддерживать список имён БД в двух
   местах.
2. **SQLite Hermes** (`kanban.db`, `state.db`) — через `sqlite3
   .backup`, не сырое копирование файла: Hermes работает в WAL-режиме,
   копирование `.db` без `.backup` может захватить БД в промежуточном
   состоянии между `.db`/`.db-wal`/`.db-shm`.
3. **Workflow n8n** — экспорт через `n8n-workflows.py export`. Неудача
   экспорта НЕ валит весь бэкап (n8n может лежать, Postgres и Hermes всё
   равно обязаны сохраниться).
4. **Данные Forgejo** — каталог docker-volume `helm_forgejo_data`
   целиком (репозитории + config + вложения PR/issue), путь резолвится
   через `docker volume inspect`, не хардкодится (демон может сменить
   data-root). БД Forgejo отдельно не нужна — она в общем кластере
   Postgres, уже в п.1. Копируется на живом сервисе без остановки: риск
   ограничен окном "push ровно в момент копирования, ref уже обновлён,
   объект ещё не скопирован" — восстанавливается из GitHub-зеркала
   (после миграции, ADR-006) или снапшота следующего дня; останавливать
   Forgejo ради этого окна дороже, чем оно стоит.
5. **Конфигурация**: `/opt/helm/config`, `/opt/helm/guardian`,
   `/etc/helm/secrets` целиком (сами секреты — в бэкапе, это НЕ
   противоречит "SECRETS_MAP без значений": карта без значений — для
   документации, бэкап обязан нести реальные значения, иначе
   восстановленный сервер не поднимется).
6. **Hermes**: `.env`, `config.yaml`, `auth.json`,
   `channel_directory.json`, `gateway_state.json`, `SOUL.md`, `cron`,
   `hooks`, `pairing`, `platforms`, `plugins`, `profiles`, `memories` —
   С ИСКЛЮЧЕНИЕМ `skills`/`derived` (регенерируемое/производное).
7. **`/opt/helm-knowledge`** — весь Vault (raw + normalized sources +
   markdown-зеркала памяти).
8. **`/opt/helm-knowledge-private`** — приватное дерево health
   (`root:helm-health 2770`). Добавлено 02.09.2026 вместе с R1: без него
   бэкап тихо потерял бы ровно те файлы, ради изоляции которых дерево и
   заведено.

## Что осознанно НЕ бэкапится

Сам установленный `~/.hermes/hermes-agent` (переустанавливается по
пинованной версии из `install.sh`), кэши (audio/image/cache), временные
sessions/sandboxes/pending_messages — runtime-мусор, не пользовательские
данные, регенерируется при следующем запуске.

## Ретеншен

`restic forget --keep-daily 7 --keep-weekly 4 --keep-monthly 6 --prune`
— по v4.0 §26.3. До 02.09.2026 держали 3 monthly (дефолт, выбранный
когда спека числа не задавала). Эти же числа называются пользователю при
удалении данных (`knowledge/offboarding.py`), и расхождение между
скриптом и обещанием ловит отдельный тест.

## Первая большая выгрузка — порциями, а не одной командой

НАЙДЕНО 02.09.2026. Яндекс.Диск нормально принимает ежедневный инкремент
(двадцать секунд) и отказывается принять разовую выгрузку в шестьдесят
мегабайт: `Fatal: unable to save snapshot: 500` на отдельных блоках после
двадцати минут повторов. Пять попыток настроить клиента — таймауты,
ограничение частоты запросов, буферизация, размер пачки — не изменили
ничего.

Помогла смена формы: `scripts/backup-seed.sh` заливает порциями по десять
файлов. Каждая успешная порция закрепляется в репозитории навсегда,
данные адресуются содержимым, повтор не отправляет уже лежащее. Те же
шестьдесят мегабайт прошли за 3 минуты 4 секунды, 19 порций из 19.

**Когда это понадобится снова.** Если корпус вырастет скачком — крупная
новая пачка, смена структуры путей, добавление нового корня в
`backup.sh`, — первый бэкап после этого делать `action=seed`, и только
потом обычный `action=backup`. Признак, что это тот случай: прогон идёт
дольше минуты.

Отдельно: оборвавшийся прогон оставляет эксклюзивный лок, из-за которого
`forget --prune` падает уже ПОСЛЕ успешного снапшота — и отметка
`last-backup` не ставится, то есть успешный бэкап выглядит
несостоявшимся. `backup.sh` снимает такие локи сам (`restic unlock`
снимает только локи мёртвых процессов).

## Как проверить, что бэкап реально восстановим

`restore_test.sh` — **не трогает продовые `/opt/helm`, `/home/helm/.
hermes`, БД**: разворачивает последний снапшот в изолированный временный
Postgres-контейнер и временный каталог, удаляет оба по выходу.

Проверки по порядку (каждая — реальный `FAIL` с ненулевым кодом выхода,
не просто предупреждение):

1. `postgres-dumpall.sql` найден и не пуст.
2. Временный Postgres поднялся — **ждёт вторую** строку "database
   system is ready to accept connections" в логе контейнера, не первый
   `pg_isready`: официальный образ на первом запуске стартует сервер
   ДВАЖДЫ (временный для init-скриптов, затем финальный) — однократная
   проверка ловит гонку на сокете временного сервера, который тут же
   гасится (найдено живьём 29.08.2026).
3. Дамп загружается без ошибок (`ON_ERROR_STOP=1`).
4. `knowledge_users`: ровно одна строка `SYSTEM_OWNER` (если таблица уже
   есть — до миграций v3.8 её нет, это не провал).
5. Ноль осиротевших `knowledge_sources` (ссылка на несуществующего
   `knowledge_user_id` — признак частично восстановленной базы, худший
   исход: выглядит рабочей, а изоляция уже не та).
6. Markdown-зеркала Micro-Memory восстановлены в количестве не меньше
   числа строк `knowledge_memories` (иначе Obsidian/будущий Graphify
   получили бы пустоту при формально целой базе).
7. Минимум 4 файла `profiles/*/config.yaml` Hermes.
8. Репозиторий Forgejo (если миграция уже прошла — до неё это не провал):
   `HEAD` разрешается, минимум один ref, `git fsck --connectivity-only`
   чист (ровно тот класс порчи, что возможен при копировании живого
   репозитория).

`touch /var/lib/helm-guardian/last-restore-test` по успеху — Guardian
читает mtime этого файла и `last-backup` для алертов о протухшем бэкапе.

## Как восстановить по-настоящему (не тест)

Скрипт restore-в-продакшен не написан — `restore_test.sh` намеренно
работает только с изолированным контейнером. Реальное восстановление —
ручная процедура тем же путём: `restic restore latest --target <dir>`,
затем `pg_dumpall`-файл грузится в реальный `helm-postgres-1` (не во
временный), Forgejo/Hermes/config файлы раскладываются по своим путям.
Пошаговый ранбук для реального аварийного восстановления — не написан,
открытый пробел этого документа (см. `TROUBLESHOOTING.md`).
