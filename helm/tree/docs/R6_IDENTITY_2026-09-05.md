# R6 — канонические личности: только сильное тождество

Распоряжение владельца 05.09.2026:

> R6 — identity only. Не чинить relation compiler. Не строить
> doctor/event relations. Не добавлять новые ML/NLI/model experiments.
> Сделать canonical identity layer + resolution candidates.
> Auto-resolution только по strong identity: same tenant, same
> entity_type, exact normalized label / exact known alias.
> Fuzzy/surname-only merge запрещён. Исходные nodes/mentions/provenance
> не мутировать и не удалять.

## Что сделано

**Три таблицы, ни одной изменённой.**

| Таблица | Смысл |
|---|---|
| `knowledge_entity_identities` | каноническая личность: тип + подпись + устойчивый UUID |
| `knowledge_entity_identity_members` | какой узел прогона отнесён к личности и **чем это доказано** |
| `knowledge_entity_resolution_candidates` | похоже, но не доказано — вопрос к человеку |

Личность вынесена в отдельные таблицы, а не в колонку узла, по прямому
требованию «не мутировать»: узел прогона остаётся ровно тем, чем его
записал разбор, а обратный ход — удаление новых строк, восстанавливать
нечего. Зеркала в схеме `health` заведены полностью: подпись врача,
известная из выписки, сама по себе медицинская информация.

**Сильное тождество — ровно два случая.** Дословное совпадение
нормализованной подписи при том же `entity_type`; дословное совпадение с
ПОДТВЕРЖДЁННЫМ алиасом (`knowledge_entity_aliases`). Ни расстояний, ни
векторов, ни моделей — новых экспериментов в R6 нет вовсе.

**Запрещённое записывается, а не теряется.** «Иванов» рядом с «Иванов
Пётр Сергеевич» и совпадение подписи при разных типах становятся
кандидатом со статусом `open`. Решает человек (устав §6).

**Разбираются только узлы текущих ревизий** (§14.20): личность из
брошенного прогона отвечала бы по тому, что графом уже не является.

## Живой прогон (270, повтор 271)

```
public   nodes_seen  0    источников с текущей ревизией вне health нет
health   nodes_seen 22    identities 15, members 22, candidates 4
         matched_by            normalized_label 22
         candidates_by_reason  surname_only 4
```

22 узла-сущности свелись к **15 личностям**: семь узлов из разных
документов оказались теми же лицами по дословному совпадению подписи.
Ни одного слияния по алиасу — алиасов извлекатель не дал. Четыре пары
«фамилия против ФИО» записаны кандидатами и НЕ слиты.

Сухой прогон и запись дали одинаковые числа. Повтор (271) дал
`already_resolved: 22` и ноль новых строк — идемпотентность подтверждена
не тестом, а живыми данными.

## Две ошибки проверки, найденные и исправленные здесь же

1. **Прогон 270** печатал `service "helm-postgres" is not running` вместо
   счётчика узлов: в скрипте стоял `docker compose exec` по имени
   сервиса, которого в compose нет. Проверка «узлы не изменились» не
   выполнялась ни разу, а лог выглядел успешным.
2. **Прогон 271**, уже с исправленным вызовом, напечатал «узлы не
   изменились: 0» — и это было верно только формально: считалась
   публичная таблица, а все 22 узла лежат в health-зеркале. Та же
   ошибка, что раньше дала `mentions_total: 0` в пилоте R5.

Снаружи эту проверку и не сделать: health-узлы видны только своей ролью
и только под выставленным RLS-контекстом. Инвариант переехал внутрь
`resolve_in()` — счёт до и после в той же сессии, расхождение поднимает
исключение. Из скрипта psql-счётчик убран: считать в public то, чего там
нет, хуже, чем не считать вовсе.

Инвариант переехал внутрь прохода и получил живое подтверждение в
прогоне 276 — см. ниже.

## Патч безопасности (владелец, 05.09.2026)

Два узких правила, архитектуру R6 не меняющие.

**Однословная подпись PERSON больше не тождество.** «Иванов» + «Иванов»
и «Иванов» + «Иванов Пётр Сергеевич» — оба случая кандидат
`surname_only`. Личность для голой фамилии всё же заводится, иначе
вопрос не к чему прицепить, но узел в её состав не входит: состав
назначает человек. Для ORGANIZATION/PLACE/CONCEPT правило не менялось —
«Инвитро» и «Москва» однословны по своей природе, это их полное имя.
Заодно исправлено `is_surname_only`: равные длины отсекались сразу, и
пара из двух одинаковых голых фамилий молча оставалась без вопроса.

**Алиас больше не сливает.** `knowledge_entity_aliases` заполняет
разбор, а не владелец, признака подтверждения у строки нет — до его
появления совпадение алиаса это кандидат новой причины
`alias_unconfirmed`. Схема подтверждения — продуктовый долг, а не часть
патча.

## Проверка перед изменением живого состояния (275)

Владелец потребовал read-only проверку без вывода имён: сколько
личностей-людей собрано под однословной подписью и сколько узлов у них
в составе. `--probe`, транзакция закрывается откатом:

```
public   person_identities 0
health   person_identities 6, one_token 1, one_token_with_members 1,
         one_token_with_members_gt1 0
```

`one_token_with_members_gt1 = 0` — ни одного слияния по однословной
подписи в живых данных нет. По условию распоряжения («если 0 — текущие
данные этим дефектом не затронуты») пересборка трёх производных таблиц
не запускалась.

## Живое подтверждение (276)

`action=maintenance script=r6-resolve.sh`: сухой прогон → запись →
повтор → та же проверка.

```
public   nodes_total  0   nodes_seen  0
health   nodes_total 47   nodes_seen 22   already_resolved 22
         identities_created 0  members_created 0  candidates_created 0
повтор — те же числа
проверка после — те же числа, что до записи
```

| Требование владельца | Чем подтверждено |
|---|---|
| `nodes_total` до == после | 47 → 47, сверяет сам проход внутри сессии; расхождение подняло бы исключение, `rc=0` |
| повтор ⇒ идемпотентно | второй проход: ноль новых строк, `already_resolved 22` |
| кандидаты сохраняются | `candidates_created 0` при непустом реестре кандидатов — строки прочитаны из базы, а не заведены заново |
| изоляция тенанта | весь проход под `bind_knowledge_user` + RLS; строк чужого тенанта в выборках нет |
| изоляция health/public | 22 узла видны только в health-сессии, в public их ноль — считать их в public было бы выносом имени врача из health |

**Чего этот прогон НЕ подтвердил, и это важнее того, что подтвердил.**
Правило «однословный PERSON не сливается» на живых данных не
исполнялось ни разу. Состав личностей собран прогонами 270/271 — до
патча; проход идемпотентен и уже отнесённый узел не пересматривает,
поэтому все 22 узла ушли в `already_resolved`, а новые правила до них
не дошли. Правило закрыто тестами (19 штук), но живого измерения у него
нет.

Отсюда же остаток: `one_token_with_members = 1` — одна личность-человек
с однословной подписью и одним узлом в составе. Слияния тут нет (узел
один), поэтому под условие пересборки этот случай не попадает. Но
строку состава по нынешним правилам проход бы не создал: узел стал бы
кандидатом `surname_only`. Практическое следствие для R7: эта личность
имеет состав, значит в ответах участвует; после пересборки — не
участвовала бы («личности без состава в ответах не участвуют»).
Пересборка разрешена владельцем только при
`one_token_with_members_gt1 > 0`, поэтому не запускалась; одна команда
`action=maintenance script=r6-rebuild.sh` приводит живое состояние к
нынешним правилам, если владелец этого захочет.

## Проверки

- 14 тестов на правила: сильное тождество (подпись, алиас), запрет
  surname-only, отказ от алиаса чужого типа, «похоже, но не кандидат»,
  структурная неприкосновенность узлов, идемпотентность, сухой прогон,
  ограничение текущими ревизиями, инвариант числа узлов.
- Реестры новых колонок добавлены в сверку public/health
  (`test_knowledge_semantic_v2_registry.py`): зеркало health написано
  вручную, public генерируется из модели, разъехаться им проще всего.
- Миграция отрендерена офлайн в SQL и сверена с DDL модели, включая
  усечённые имена внешних ключей.
- `alembic upgrade head` и `setup-health-role.sh` прошли на сервере;
  `helm_app` не читает ни одну из трёх новых health-таблиц (`f` везде).

## Расхождение контракта recon — закрыто

`action=recon` был объявлен «read-only по контракту», но принудительно
запрещал только скрипты с именем `destructive-*`. И пилот R5, и проходы
270/271 — записывающие, все шли через `recon`. По распоряжению
владельца заведено отдельное действие `action=maintenance`: обратимые
аддитивные операции с записью идут им, со снятой точкой возврата;
`recon` остаётся диагностикой. Прогон 276 — первый по новому контракту.

## Итог

**R6 = DONE.** Основание — условие владельца: «после этого R6 = DONE
независимо от количества unresolved candidates». Живой проход чист,
инвариант неприкосновенности узлов подтверждён измерением,
идемпотентность подтверждена повтором, слияний по однословной подписи в
данных нет. Незакрытый долг назван выше поимённо: новые правила
тождества живого измерения пока не получили.
