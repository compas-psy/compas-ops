## Побочная находка того же дня: пересчёт v3 сломал структурный ответ

Не этап, но обязано быть записано — это ровно тот случай, когда
служебная метрика выросла, а пользовательский результат пропал.

Утром бот на «каких врачей я посещал?» отвечал списком из пяти врачей.
После доведения semantic-v3 до 90/90 тот же вопрос вернул ровно
`NOT_FOUND`. Инструментовка самого ответа (прогон 345):

```
path_used none, graph_edges 8, items 0
considered: личности-люди с составом 0, узлы в их составе 0
skipped:    узел графа без канонической личности 8
```

Врачебные рёбра на месте. Личностей с составом — ноль. Пересчёт
переключил текущие ревизии у всех 90 источников, а слой личностей R6
остался над узлами прежнего поколения; `query_router` берёт узлы
текущей ревизии и не находит ни одной личности.

Пересборка R6 (прогон 346) прошла все три гейта: `rc=0 idem=0
residue=0`. После неё:

| | утро | после v3, до R6 | после R6 |
|---|---|---|---|
| items | 5 | 0 | 29 |
| источники в ответе | поля нет | 0 | 35 спанов |

**Вывод для порядка работ:** переключение поколения узлов обязано
тянуть за собой пересборку производных слоёв в той же операции. Пока
это ручная последовательность из двух прогонов, между которыми живой
ответ пуст. Закрывается в P2 вместе с очередью: READY семантики ставит
задание на разрешение сущностей.

## P2 — обычная загрузка сама порождает семантику

**Статус: ACCEPTED** по проводке, транспорт — та же оговорка, что у P1.

| | |
|---|---|
| repo SHA | `8a28b27` (код), `cfb54bc` (приёмка) |
| deployed SHA | `8a28b277f1b24500aef3f07e2896ab19c9d1fc6a` |
| alembic head | `d7c02f9a41be` |
| прогоны | выкат 348, миграция 349, приёмка 352 |
| регрессии | 818 тестов (было 813); пять новых идут по AST; саботаж уронил ровно те две, что обязаны |

Что было. `worker.py::process_job` звал `atomize_and_store()` —
замороженный с R2 и возвращающий 0 (`atomizer.py:411`). Настоящий
`publish_semantic_run()` вызывали три ручных CLI. Любой новый файл
останавливался на L1; корпус из 90 источников существовал потому, что
backfill запускали руками.

Что доказано живьём (прогон 352):

```
таблица очереди: есть        источник зарегистрирован, создан=True
L1-задание: done             задание разбора: done
текущая ревизия: есть        узлов в ревизии: 7
повторная загрузка: created=False, заданий разбора 1
```

Журнал воркера: L1 `done` в 16:30:06, семантика `ready (switched=True)`
в 16:30:46, затем `done`. Сорок секунд от файла до знания, **ни одной
команды backfill**. Повтор тех же байтов не создал ни второго источника,
ни второго задания.

Чего НЕ доказано: вход через чат. Файл зарегистрирован той же функцией,
которой пользуется приём из Telegram, но не через сам Telegram —
причина та же, что у P1.

Две ошибки были в самой приёмке, не в коде, и обе стоили прогона: файл
лежал в `/tmp` контейнера `helm-core`, а читает его воркер (прогон 350);
привязка тенанта транзакционно-локальная и после `commit()` снимается,
из-за чего RLS спрятал собственную строку и напечатал «заданий 0» там,
где задание отработало (прогон 351).

## P2 — восстановление очереди после падения воркера

**Статус: ПРИНЯТО ЖИВЬЁМ.** Прогон 377, сценарий владельца дословно.

Дыра: `claim` брал только `PENDING`, а `RUNNING` фиксировался коммитом
ДО разбора. Воркер, убитый между этим коммитом и концом разбора,
оставлял задание в `RUNNING` навсегда — вернуть работу можно было только
руками.

```
задание разбора: 5c5de719…       поставлено воркером после парсинга, не руками
состояние: running|1|19:49:47    аренда на 30 минут выдана
воркер убит → задание: running   ревизий на источник: 0
аренда сдвинута в прошлое        единственный SQL проверки
воркер поднят → итог: done|2     вторая попытка, доведено до конца
ревизий стало: 1 (было 0) · текущая ревизия есть · зависших в running: 0
```

Настоящие в проверке: падение посреди разбора, потеря владения,
повторное взятие, доведение до конца, отсутствие дубля результата.
Ускорено ровно одно — срок аренды сдвинут в прошлое одним UPDATE, иначе
пришлось бы ждать тридцать минут. Ни статус задания, ни ревизия руками
не трогались.

**Находка попутно: `ingest_text()` семантику породить не может.** Он
записывает `source_path`, но самого файла туда не кладёт; `source_text()`
читает путь с диска, не находит и возвращает `None`, задание падает в
`NoText` (прогон 376). Настоящая загрузка файла идёт через
`register_file_for_ingest` и работает. Записано как отдельный дефект, не
чинилось в этом шаге.

## P3.1 — даты: измеренный тупик, и что сделано вместо

не пишется: 33 узла из 522 при структурном потолке 490. Два замера на

Коротко: 112 окон из 122 содержат дату, но 105 не содержат даты
события. Корпус пишет дату бланка (83 якоря), рождения и норматива

весь корпус. Информации, которая нужна правилу, в источнике нет; это не
недоработка извлечения.

**Сделано вместо, и замер сделал это срочным.** Вопрос с периодом,
который отбор применить не умеет, больше не отвечается молча по всему

Тот же прогон показал замер вживую: «в 2025 году» → «Не нашёл… В данных

## Перечанковка поискового слоя (задача #151, пункт P3 аудита)

**Статус: ВЫКАЧЕНО И ПРИНЯТО ЧАСТИЧНО.** Корень плохих ответов, найденный

**Что стало лучше на живых ответах** (прогоны 365 и 367):

- «какое у меня было давление?» → Z0, «У меня давление 120/80 мм рт. ст.»
  с источником-консультацией кардиолога. Обычный факт отвечается.
- Механизм 05.09 сломан: пять структурно одинаковых строк бланка больше
  не получают одинаковый ранг и не занимают весь колчан.
- Заголовок теперь едет вместе со строкой: «ОСМОТР ХИРУРГА ⏎ Врач: …».
- Векторная ветка снова запрашивается: бракованная лексика чистится ДО
  подсчёта «колчан полон», а не после (прежний порядок опирался на
  замер 307, который тот же разбор потом опроверг сам).
- Соседний слой цел: структурный ответ — те же 29 врачей. Проверено
  отдельно, потому что в тот же день переключение semantic-v3 уже
  обрушило слой личностей при целых данных.

**Что НЕ починилось, и это главное.** Вопрос владельца «что там прописал
врач?» ответа по-прежнему не получает: ближайшее — блок «ПОДПИСИ». Две
причины, обе за пределами нарезки:

1. В чанке с назначениями слова «врач» нет, а OR-поиск идёт по основам
   вопроса — поднимаются подписи. Это ранжирование, а не нарезка.
2. Заголовок обрывает склейку, а в бланке идёт подряд «ОСМОТР ХИРУРГА /
   Врач: ФИО ____ / ОСМОТР ТЕРАПЕВТА»: секция-заглушка остаётся коротким
   чанком. Остаток небольшой (3 чанка короче 20 символов из 366), но
   именно он населяет этот вопрос.

Ответ при этом честно назван «Не нашёл прямого ответа. Ближайшее из ваших
записей» — контракт работает, пользы в ответе нет.

**Побочная находка прогона 367: P1 доставлен наполовину.** Все 35
источников структурного ответа уходили наружу как `kind: "span"` с
`window_id`, `char_start`, `char_end` равными `None`. Путь графа точных
границ не имеет — доказательством там служит ребро, и `edge_id` в
`Proof` есть, но терялся. Исправлено: источник называется тем, что он
есть, `edge` или `span`.
