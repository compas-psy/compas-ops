### Находка 1: у двух репозиториев default branch — агентская ветка

У `zapiski` и `signalAI-mobileApp` HEAD указывает не на `main`, а на
ветку вида `claude/*`. Миграция перенесёт это состояние как есть, и в
Forgejo default branch окажется тем же. Это не ошибка миграции — это
текущее состояние GitHub, и менять его молча нельзя: у `zapiski`
половина workflow триггерится именно на эту ветку (см. ниже), то есть
она реально рабочая, а не забытая.

**Решение владельца требуется до шага 11** (переключение primary
remote): оставить как есть или привести default branch к `main`. Пока
не решено — миграцию это не блокирует.

### Находка 2: 309 веток в signalAI-mobileApp

Зеркальная миграция перенесёт все 309. Технически это работает и
`push mirror` вернёт их обратно на GitHub без расхождений. Вопрос
только в том, нужна ли эта история веток в новом primary: чистка перед
миграцией дешевле, чем после (после — придётся удалять в двух местах).
Решение владельца, не блокирует.

### Находка 3: GitHub Issues — активная панель управления signalAI

Шесть workflow этого репозитория триггерятся на `issue_comment` и
`workflow_run` (`owner-commands.yml`, `runtime-ab-audit.yml`,
`runtime-calendar.yml`, `runtime-funnel.yml`,
`runtime-release-command.yml`, `sideload-status-report.yml`). То есть
GitHub для `signalAI-mobileApp` — не только зеркало кода, но и рабочий
интерфейс команд владельца.

§18.3 прямо говорит: «PR metadata не считается Git и автоматически не
зеркалится». То же верно для issue-комментариев. После переключения
primary на Forgejo эти команды продолжат работать **только на
GitHub-стороне**, и это надо либо принять сознательно, либо перенести
механизм. Практический вывод: `signalAI-mobileApp` мигрировать
последним, отдельным решением.

## Шаг 1 (частично): открытые PR

Проверить удалённо не удалось: GitHub API в этой сессии доступен только
для `compas-ops` (у него открытых PR нет — проверено). Для остальных
четырёх инвентаризация открытых PR выполняется самим
`forgejo-migrate.py` на сервере: он печатает номер, заголовок и URL
каждого открытого PR перед миграцией репозитория. Этот вывод —
обязательная часть данного лога (§18.3: «URL/history сохранить»).

## §18.5. Проверка workflow triggers — выполнена

§18.5 требует убедиться, что CI умеет запускаться от **mirrored branch
SHA**, а не только от `pull_request` (который зеркало не создаёт).

Хорошая новость: **ни одного workflow, работающего только на
`pull_request`, нет ни в одном репозитории**. Обходной путь, который
§18.5 разрешает добавлять («safe push/manual exact-ref path»), не нужен.

| Репозиторий | всего | on: push | только workflow_dispatch | только pull_request |
|---|---|---|---|---|
| `cmpas.ru` | 9 | 8 | 1 | 0 |
| `compas-voice` | 1 | 1 | 0 | 0 |
| `zapiski` | 6 | 6 | 0 | 0 |
| `signalAI-mobileApp` | 22 | 3 | 13 | 0 (+6 на `issue_comment`/`workflow_run`) |

### Находка 4: push-workflow привязаны к main — CI на feature-ветке не запустится

Все `on: push` workflow отфильтрованы по веткам: `branches: [main]`
(либо конкретной `claude/*` у `zapiski`, либо только по тегам `v*` у
`signalAI`). Ни один не запускается на произвольной ветке.

Для миграции это безопасно: деплой-workflow и не должны срабатывать на
feature-ветках — это было бы опасно, а не полезно. Но это ломает
сценарий §18.6/§19 на шаге «feature branch → Forgejo PR → mirrored SHA
CI in GitHub → exact SHA green»: зеркальный push feature-ветки не
создаст **ни одного** запуска, и условие «зелёный CI на точном SHA»
никогда не выполнится — не потому, что упало, а потому, что проверять
нечего.

Причина в том, что среди этих workflow вообще нет тестового: у
`cmpas.ru` восемь — это build/deploy/db/provision, у `zapiski` —
build/deploy/provision + security, у `signalAI` `quality.yml` есть, но
только `workflow_dispatch`.

**Вывод:** миграция (P6.5) этим не блокируется — деплой с `main` через
зеркало продолжит работать как раньше. Но lane разработки (P8) требует
в каждом репозитории workflow, запускаемый на любой ветке и проверяющий
код, а не выкатывающий его. Это отдельная задача P8, не миграции; её
нельзя закрыть «добавлением push-триггера» к существующим — они
деплоят.
