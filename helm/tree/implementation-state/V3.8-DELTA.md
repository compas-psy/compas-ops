## Находка до кода: RLS не подействует без FORCE (владелец таблиц = роль приложения)

`compose/init/01-databases.sql` создаёт единственную runtime-роль
`helm_app` с `GRANT USAGE, CREATE ON SCHEMA public` — она же выполняет
`alembic upgrade head`, то есть она же ВЛАДЕЕТ всеми таблицами Knowledge.
PostgreSQL RLS по умолчанию **не ограничивает владельца таблицы**,
независимо от количества `CREATE POLICY` — обычная ловушка, которая
сделала бы RLS декоративным, а не defense-in-depth, как явно требует
спека ("User-facing DB role cannot bypass RLS").

Комментарий в том же файле («для единоличной системы разница между
'может создавать таблицы' и 'не может' не даёт реальной защиты») был
верен ДО мультитенантности — v3.8 явно эту предпосылку снимает.

Решение (минимальный blast radius, не переделывает роль/пул
подключений): `ALTER TABLE ... FORCE ROW LEVEL SECURITY` на всех
tenant-scoped таблицах — форсирует применение политик даже к владельцу
(суперпользователь всё равно обходит RLS всегда, но `helm_app` не
суперпользователь). Полноценное разделение "миграционная роль" vs
"runtime-роль с ограниченными правами" — отдельная, более крупная
инфраструктурная задача (пришлось бы менять пул подключений/секреты),
не блокирует то, что RLS реально работает уже сейчас.

Механизм принадлежности сессии: Postgres session GUC
`app.current_knowledge_user_id`, выставляется через `set_config(...,
true)` (эквивалент `SET LOCAL`, но параметризуемо — сам `SET LOCAL x =
:v` bind-параметры не принимает) в начале транзакции запроса; политики
RLS сверяются с `current_setting('app.current_knowledge_user_id',
true)::uuid`. Единая точка входа — `bind_knowledge_user()`
(`helm_core/knowledge/tenancy.py`): разрешает тенанта по умолчанию в
SYSTEM_OWNER И сразу привязывает GUC, чтобы explicit-предикат в коде и
RLS-GUC никогда не расходились по разным call sites.

**Находка в процессе (пул соединений)**: `current_setting(..., true)`
возвращает NULL только пока кастомный GUC вообще НИ РАЗУ не был
затронут в сессии/соединении. На пуле соединений (SQLAlchemy — и в
проде, и в pytest, где `helm`-роль намеренно понижена до NOSUPERUSER,
чтобы тесты реально гоняли RLS, а не обходили его как суперпользователь)
одна и та же физическая связь переживает несколько логических
транзакций — после ПЕРВОГО `set_config(..., true)` на связке Postgres
заводит placeholder с дефолтом `''` (пустая строка), не NULL; следующая
транзакция без своего `bind_knowledge_user()` видит `current_setting(...)
= ''`, и `''::uuid` — ОШИБКА каста (падение запроса), не тихий NULL.
Поймано живым прогоном тестов (`test_webhook_calls_chief_when_probe_
finds_nothing` и ещё 9 упали с `InvalidTextRepresentation` при первом
включении RLS в тестовой схеме). Правка: предикат — `knowledge_user_id =
NULLIF(current_setting(...), '')::uuid` (`helm_core/knowledge/rls.py`)
— `NULLIF` схлопывает обе формы "не тронуто" в один NULL, `knowledge_
user_id = NULL` даёт NULL (fail closed: ноль строк), не падение. Это не
только тестовый артефакт — то же самое ждало бы прод под пулом
соединений Uvicorn/SQLAlchemy при любом ЕЩЁ не обвязанном call site.

Фоновый воркер (`helm-knowledge-worker`) — `process_job()` тоже зовёт
`bind_knowledge_user(session, job.knowledge_user_id)` в самом начале
(immutable поле уже существующего durable job'а — спека явно разрешает
опираться на него: "Background workers may use a service role only when
a durable job already contains immutable knowledge_user_id"), поэтому
разбор физически не может задеть чужой source, даже если вызывающий код
до этого был привязан к другому тенанту (проверено тестом, см. ниже).

**Осознанное отступление от буквы спеки, не молчаливое**:
`claim_next_job()` — сам ПОИСК следующей PENDING-задачи, БЕЗ ещё
известного job'а — спека одобряет здесь ИМЕННО "service role"
(отдельная Postgres-роль с `BYPASSRLS`, для кросс-тенантного claim).
Такая роль — реальная инфраструктура (новая роль, новый секрет, правки
`compose/init/01-databases.sql` и `docker-compose.yml`), а вводить её
сейчас ради возможности, которой ещё физически неоткуда взяться (второй
живой пользователь с собственной очередью появится только в P8.6.4 —
задача #19, ещё не начата), было бы инфраструктурой без потребности
(CLAUDE.md §2). Вместо этого `claim_next_job()` привязывает GUC к
SYSTEM_OWNER (`bind_knowledge_user(session, None)`) перед поиском —
сегодня, когда SYSTEM_OWNER — единственный тенант, у которого вообще
может быть очередь, это не отличимо от "видеть все очереди". Эту же
строку придётся заменить настоящим fair-queue claim'ом (или service-
role) в P8.6.4 — явно помечено комментарием в коде, не тихий пробел.

(`_active_tenant_ids()` + `_last_served_tenant_index`, модульное
состояние процесса, не персистентное) вместо глобального FIFO —
"one user's large ZIP does not starve another user's short upload".
Для сегодняшнего единственного реального тенанта (SYSTEM_OWNER)
поведение не отличается от прежнего FIFO — ноль риска регрессии на
существующем пути, подтверждено полным сьютом без единого нового
провала. `process_job()`'s собственная привязка к `job.knowledge_
user_id` (v3.8 Фаза 1) не изменилась — round-robin касается только
ВЫБОРА следующего job'а, не его обработки.

`knowledge/onboarding.py::suspend_user()`/`reactivate_user()` +
`POST /internal/knowledge/users/{id}/suspend`/`.../reactivate` —
раньше "suspended" было тестируемо только прямой мутацией БД в тестах,
теперь есть реальное действие. `reactivate_user()` намеренно не трогает
`DELETED` (RED-действие, отдельное, необратимое) — тихий обход через
reactivate был бы неверным.

**Evidence P8.5.12 recall (30.08.2026)**: до этого захода Micro-Memory
писалась корректно, но не читалась ничем, кроме прямых тестов —
обычный вопрос владельца («Дай мне ссылку про титры») искал только
`KnowledgeChunk`. Пробел закрыт: `helm_core/knowledge/recall.py` +
подключение в `probe()`. §14.10 "retrieval **also checks `expires_at`
against current user-local time at query time**" реализовано именно
предикатом запроса, а не доверием к фоновой рутине — рутины,
материализующей `status=EXPIRED`, в кодовой базе нет вовсе, и тест это
фиксирует явно (истёкшая запись остаётся `ACTIVE` в БД и всё равно не
попадает в текущий recall). Исторический вопрос («Какой был номер
вчера?») дополнительно допускает `EXPIRED`/`SUPERSEDED`, но никогда —
`DISABLED`/`DELETED`: явно забытое не должно всплывать от
формулировки.

§14.13 REMINDER_TASK: подсистемы задач/напоминаний в HELM нет вовсе,
поэтому «маршрутизация» выражена единственным способом, который не
врёт, — не отвечать из памяти и эскалировать. Детектор требует
совпадения ТРЁХ признаков сразу («напомни» + будущий момент +
инфинитив), потому что каждый по отдельности встречается и в законном
вопросе к памяти: собственный пример спеки «номер машины курьера,
который приедет **сегодня**» содержит и «напомни», и «сегодня», оставаясь
recall'ом. Асимметрия ошибок сознательная: «не распознали напоминание»
не теряет ничего (создавать напоминание всё равно нечем), «съели
вопрос к памяти как напоминание» потеряло бы ответ.

Осознанные упрощения (не тихие): семь намерений §14.13 сведены к двум
предикатам — за `DOCUMENT_REQUEST` (§14.15) и `KNOWLEDGE_ADMIN`
(§14.16) не стоит никакой реализации, `LIVE_EXTERNAL` не имеет
коннектора, классификатор на семь веток с пятью сходящимися в одну
точку был бы абстракцией ради одного применения. §14.12 "deterministic
rank fusion" между памятью и документами не строится: память имеет
абсолютный приоритет — спека требует "strong exact/recency/validity
boost", абсолютный приоритет и есть сильнейший из возможных, при этом
объяснимый, в отличие от весов, которые нечем откалибровать (golden-
набора нет, §30.8.5). Уточняющий вопрос при неоднозначности (§14.13
"ask one local clarification") не реализован — требует pending-
состояния канала, как `chat_intake.py` для вложений.

Единственное попадание возвращается ДОСЛОВНО (`answer_text ==
canonical_text`, проверено равенством, а не вхождением) — §14.14
"exact URL/identifier not modified": любая приписка вокруг ссылки
делает ответ уже не тем, что владелец сохранил. Ноль платного AI здесь
не проверка в рантайме, а конструкция: в `probe()`/`recall.py`
переписывать текст попросту нечем. 370/370 тестов зелёных (было 350),
20 новых в `tests/test_knowledge_recall.py` — все четыре фикстуры
acceptance-списка «Recall» из спеки дословно, плюс tenant-изоляция
recall (память одного пользователя не находится вопросом другого) и
регрессия документного пути.

Не реализовано этой частью (явно): голосовой recall (GigaAM нигде не
подключён), `last_used_at` не обновляется при чтении (поле никто не
читает), `KNOWLEDGE_USER`-специфичный стиль ответа (P8.6.6).

**Расширение §10.5.8.1 на действия без одобрения.** Прежний step-up
существовал только для одобрений: `AssertOptionsIn.approval_ids`
требовал непустой список, а `StepUp.assert_binds()` привязывал церемонию
к конкретному `approval_id`. Для раздела «Пользователи» одобрений нет, и
самым простым путём было бы взять `require_stepup` без привязки вовсе —
но тогда подтверждение, полученное на «пригласить», подошло бы к
«приостановить», а полученное на приостановку пользователя A — к
приостановке B. Вместо этого добавлен `StepUp.assert_scope()` (то же
правило, тот же `hmac.compare_digest`), а scope включает идентификатор
цели: `panel:users:suspend:<uuid>`. `approval_ids` теперь допускает
пустой список — это сужение, а не расширение: такой challenge не может
одобрить ничего, потому что `assert_binds()` ищет `approval_id` в
пустом списке и отказывает. Оба направления промаха проверены тестами
(церемония «пригласить» → suspend = 403; церемония на пользователя B →
suspend A = 403).

`SYSTEM_OWNER` показывается в списке (его расход места владельцу видеть
полезно), но suspend/квота для него отвечают 409: приостановка владельца
закрыла бы ему доступ к собственному HELM'у из интерфейса, задуманного
для чужих учёток, и откатить это было бы уже нечем — панель после
этого недоступна.

**Находка (не исправлена, заведена явно)**: `knowledge_user_usage`
содержит `sources_count`/`memories_count`/`queued_jobs`, которые никто
не обновляет — `quotas.py` ведёт только `storage_bytes` и
`ingest_bytes_today`. Панель их не показывает вовсе: вечный ноль в
интерфейсе владельца хуже отсутствующего поля. Либо счётчики надо
начать вести, либо убрать из схемы — отдельным решением, не тихо в этом
заходе.

**НЕ реализовано: Knowledge-only оболочка панели для KNOWLEDGE_USER.**
Это не «не успели», а упор в решение, которое агент не вправе принять
за владельца. Вход в панель сегодня — Telegram Login Widget с проверкой
`owner_id` + passkey (`api/auth.py`): единственная существующая дверь
проверяет, что вошедший — ВЛАДЕЛЕЦ. Чтобы secondary-пользователь мог
войти, нужен второй путь enrollment'а, а это выбор в области
безопасности с необратимыми последствиями:

- через Dedicated Knowledge Bot (одноразовый deep-link, как инвайт) —
  тогда passkey-регистрация панели начинается из Telegram-бота, и
  компрометация бота становится путём к панели;
- через отдельный enrollment-токен от владельца — ещё один секрет,
  который надо доставить человеку вне HELM;
- вовсе без панели для secondary — весь Второй мозг такого
  пользователя живёт в боте (сегодняшнее фактическое состояние).

Директива владельца прямо запрещает ослаблять owner-вход ради
secondary-пользователей, а любой из вариантов трогает именно вход. К
тому же Knowledge-UI не существует и для самого владельца (P8.5.8 «Panel
строка Knowledge» — ❌), так что оболочка «свои документы/память/
архивы/настройки» строилась бы с нуля и вслепую для пользователя,
который пока не может войти. Вопрос вынесен владельцу; до его ответа
KNOWLEDGE_USER работает через бота, как и был задуман (§9.0 «transport
adapter»).

## Осознанно упрощено против буквы спеки

- `primary_domain_id`/per-user `knowledge_domains`/`knowledge_topics` —
  НЕ строится (то же решение, что в `V3.7-DELTA.md`: реестра доменов
  нет и не вводится этим заходом). `KnowledgeMemory.domain` — `str`
  через существующий `KnowledgeDomain` enum, как везде в кодовой базе,
  nullable — не блокирует запись при отсутствии совпадения.
- Векторный/embedding слой Micro-Memory ("direct FTS/vector unit") —
  только FTS (`tsvector`, тот же паттерн, что `KnowledgeChunk`).
  pgvector/embeddings (P8.5.4 остаток) не реализованы ни для
  документов, ни для памяти — не новый пробел, уже задокументированный.
- Ollama structured classifier для неоднозначных `Запомни`-команд — не
  реализован (Ollama вообще не установлен, P8.5.6 remains design-only,
  `docs/KNOWLEDGE_MODELS.md`). Классификация — детерминированные
  префиксы/regex (`Запомни`/`/remember`/`Сохрани в память`/`Не забудь`),
  без LLM вообще; неоднозначные случаи получают короткий уточняющий
  вопрос, не угадывание.
- Cross-user physical dedup намеренно НЕ реализуется — спека сама явно
  говорит "intentionally not implemented in v1", совпадает с нашим
  подходом без доп. усилий.
- Инвайт создаётся HMAC-подписанным internal API-вызовом, не формой в
  Panel (P8.6.5 не начат) — сама спека допускает этот промежуточный шаг
  ("activation remains owner-interactive pending").
- Файлы/ZIP/голос для KNOWLEDGE_USER через Dedicated Bot — НЕ
  реализованы (см. ADR-025: нужен отдельный raw-HTTP Telegram file-
  download, которого этот вебхук сегодня не делает); вложение получает
  явный "пока не поддерживается" ответ, не тихо игнорируется.
