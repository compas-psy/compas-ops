## Находка до кода: RLS не подействует без FORCE (владелец таблиц = роль приложения)

`compose/init/01-databases.sql` создаёт единственную runtime-роль
`helm_app` с `GRANT USAGE, CREATE ON SCHEMA public` — она же выполняет
`alembic upgrade head`, то есть она же ВЛАДЕЕТ всеми таблицами Knowledge.
PostgreSQL RLS по умолчанию **не ограничивает владельца таблицы**,
независимо от количества `CREATE POLICY` — обычная ловушка, которая
сделала бы RLS декоративным, а не defense-in-depth, как явно требует
спека ("User-facing DB role cannot bypass RLS").

Комментарий в том же файле («для единоличной системы разница между
'может создавать таблицы' и 'не может' не даёт реальной защиты») был
верен ДО мультитенантности — v3.8 явно эту предпосылку снимает.

Решение (минимальный blast radius, не переделывает роль/пул
подключений): `ALTER TABLE ... FORCE ROW LEVEL SECURITY` на всех
tenant-scoped таблицах — форсирует применение политик даже к владельцу
(суперпользователь всё равно обходит RLS всегда, но `helm_app` не
суперпользователь). Полноценное разделение "миграционная роль" vs
"runtime-роль с ограниченными правами" — отдельная, более крупная
инфраструктурная задача (пришлось бы менять пул подключений/секреты),
не блокирует то, что RLS реально работает уже сейчас.

Механизм принадлежности сессии: Postgres session GUC
`app.current_knowledge_user_id`, выставляется через `set_config(...,
true)` (эквивалент `SET LOCAL`, но параметризуемо — сам `SET LOCAL x =
:v` bind-параметры не принимает) в начале транзакции запроса; политики
RLS сверяются с `current_setting('app.current_knowledge_user_id',
true)::uuid`. Единая точка входа — `bind_knowledge_user()`
(`helm_core/knowledge/tenancy.py`): разрешает тенанта по умолчанию в
SYSTEM_OWNER И сразу привязывает GUC, чтобы explicit-предикат в коде и
RLS-GUC никогда не расходились по разным call sites.

**Находка в процессе (пул соединений)**: `current_setting(..., true)`
возвращает NULL только пока кастомный GUC вообще НИ РАЗУ не был
затронут в сессии/соединении. На пуле соединений (SQLAlchemy — и в
проде, и в pytest, где `helm`-роль намеренно понижена до NOSUPERUSER,
чтобы тесты реально гоняли RLS, а не обходили его как суперпользователь)
одна и та же физическая связь переживает несколько логических
транзакций — после ПЕРВОГО `set_config(..., true)` на связке Postgres
заводит placeholder с дефолтом `''` (пустая строка), не NULL; следующая
транзакция без своего `bind_knowledge_user()` видит `current_setting(...)
= ''`, и `''::uuid` — ОШИБКА каста (падение запроса), не тихий NULL.
Поймано живым прогоном тестов (`test_webhook_calls_chief_when_probe_
finds_nothing` и ещё 9 упали с `InvalidTextRepresentation` при первом
включении RLS в тестовой схеме). Правка: предикат — `knowledge_user_id =
NULLIF(current_setting(...), '')::uuid` (`helm_core/knowledge/rls.py`)
— `NULLIF` схлопывает обе формы "не тронуто" в один NULL, `knowledge_
user_id = NULL` даёт NULL (fail closed: ноль строк), не падение. Это не
только тестовый артефакт — то же самое ждало бы прод под пулом
соединений Uvicorn/SQLAlchemy при любом ЕЩЁ не обвязанном call site.

Фоновый воркер (`helm-knowledge-worker`) — `process_job()` тоже зовёт
`bind_knowledge_user(session, job.knowledge_user_id)` в самом начале
(immutable поле уже существующего durable job'а — спека явно разрешает
опираться на него: "Background workers may use a service role only when
a durable job already contains immutable knowledge_user_id"), поэтому
разбор физически не может задеть чужой source, даже если вызывающий код
до этого был привязан к другому тенанту (проверено тестом, см. ниже).

**Осознанное отступление от буквы спеки, не молчаливое**:
`claim_next_job()` — сам ПОИСК следующей PENDING-задачи, БЕЗ ещё
известного job'а — спека одобряет здесь ИМЕННО "service role"
(отдельная Postgres-роль с `BYPASSRLS`, для кросс-тенантного claim).
Такая роль — реальная инфраструктура (новая роль, новый секрет, правки
`compose/init/01-databases.sql` и `docker-compose.yml`), а вводить её
сейчас ради возможности, которой ещё физически неоткуда взяться (второй
живой пользователь с собственной очередью появится только в P8.6.4 —
задача #19, ещё не начата), было бы инфраструктурой без потребности
(CLAUDE.md §2). Вместо этого `claim_next_job()` привязывает GUC к
SYSTEM_OWNER (`bind_knowledge_user(session, None)`) перед поиском —
сегодня, когда SYSTEM_OWNER — единственный тенант, у которого вообще
может быть очередь, это не отличимо от "видеть все очереди". Эту же
строку придётся заменить настоящим fair-queue claim'ом (или service-
role) в P8.6.4 — явно помечено комментарием в коде, не тихий пробел.

цели: `panel:users:suspend:<uuid>`. `approval_ids` теперь допускает
пустой список — это сужение, а не расширение: такой challenge не может
одобрить ничего, потому что `assert_binds()` ищет `approval_id` в
пустом списке и отказывает. Оба направления промаха проверены тестами
(церемония «пригласить» → suspend = 403; церемония на пользователя B →
suspend A = 403).

**Evidence P8.6.7 остаток (30.08.2026)**: `helm_core/knowledge/
offboarding.py` — зеркало `onboarding.py`. Порядок спеки `suspend →
optional export → explicit RED delete` соблюдён не документацией, а
кодом: удаление отказывается работать, пока аккаунт не приостановлен, и
отдельно требует явного ответа, что с выгрузкой. Оба шага в панели
появляются только у приостановленного пользователя — тот же порядок,
видимый глазами.

**Решение, вынесенное владельцу: удаление НЕ идёт через approval
engine, хотя спека называет его RED.** Approval engine существует для
случая «агент хочет сделать — владелец подписывает». Здесь инициатор
сам владелец, лично, из своей панели, со свежим passkey. Провести это
через реестр действий значило бы завести путь, которым агент МОЖЕТ
предложить уничтожение чужого аккаунта, — сейчас такого пути нет вовсе,
и это сильнее любой записи одобрения. Защита не слабее, просто другая:
предварительная приостановка (два разнесённых во времени решения),
passkey, привязанный именно к этому пользователю, и обязательный явный
ответ про выгрузку. Если владелец предпочтёт полный RED-путь через
реестр — переделка локальная, executor и запись в `actions.yaml`.

Выгрузка кладётся файлом на диск и **её содержимое в панель не
возвращается**: §14.3 запрещает владельцу обычный просмотр чужого
Второго мозга, а выгрузка нужна, чтобы отдать данные их хозяину. Создать
архив может только владелец — после приостановки человек уже не войдёт.
Тест проверяет и это (в ответе эндпоинта нет ни одной записи памяти), и
отсутствие чужих данных внутри архива.

Оригинальные файлы (L0 RAW) в архив не кладутся — это гигабайты, и
выгрузка стала бы копией всего хранилища. Вместо них полный перечень с
именами, размерами и SHA256. Названо прямо в манифесте, чтобы человек не
решил, будто получил всё.

Строка удалённого пользователя остаётся с пометкой `DELETED`, а не
исчезает: надгробие держит внешние ключи, отвечает «кто и когда был
удалён» и не даёт переиспользовать идентификатор. Содержимого за ним
нет — ни строк, ни файлов, ни сессий, ни passkey, ни привязок каналов.

**Раскрытие сроков хранения** (§14.3 "backup-retention disclosure"):
названный человеку срок обязан совпадать с реальной политикой
`restic forget` в `scripts/backup.sh`. Расхождение здесь — не рассинхрон
констант, а неверное обещание живому человеку про его данные, поэтому
за этим следит тест, который читает сам скрипт и сверяет три числа.

**Найденный по пути дефект тестов**: часть тестов вызывала
`try_remember()` и выгрузку без явного `vault_root` и создавала каталоги
прямо в `/opt/helm-knowledge`. На машине разработчика это означало бы,
что прогон тестов подмешивает мусор в реальные заметки владельца.
Починено так, чтобы стало невозможным: значения по умолчанию в
сигнатурах заменены на `None` с разрешением при вызове (иначе подмена не
подействовала бы — значение по умолчанию вычисляется один раз, при
определении функции), плюс autouse-фикстура в `conftest.py`
перенаправляет корень хранилища во временный каталог на весь прогон.
Проверено: после полного прогона в `/opt/helm-knowledge` не появляется
ничего.

**Evidence §14.16 управление памятью словами (30.08.2026)**:
`helm_core/knowledge/admin.py`. До этого жизненный цикл Micro-Memory был
разомкнут — «Запомни» умел создавать, а состояние «забыто» существовало
в схеме, но достичь его можно было только правкой базы руками. Тот же
запах, что был у «приостановленного пользователя» до P8.6.4, и починен
так же: появилось реальное действие.

Четыре команды: `Забудь`/`Не используй` (обратимо), `Верни в память`/
`Восстанови`, `Удали навсегда` (физическое удаление), `Исправь … : …`.
Подключены во все три входа — MAX владельца, Telegram владельца (через
новый `POST /internal/knowledge/admin`, потому что плагин живёт вне
процесса Control Plane) и Dedicated Knowledge Bot.

**Порядок разбора имеет значение дважды.** «Удали навсегда» проверяется
раньше обратимых команд — иначе необратимое действие уходило бы в
обратимую ветку по совпадению более короткого префикса. И весь блок
стоит ПОСЛЕ «Запомни», но ДО обычного вопроса: «Забудь про код
домофона», попав в поиск, было бы понято как просьба этот код НАЙТИ —
ровно наоборот сказанному. Якорь на начало строки решает конфликт «Не
забудь купить молоко» (это «запомни») против «Забудь про молоко» без
отдельной проверки.

Цель ищется тем же полнотекстовым поиском, что и recall, по своему
тенанту. Одно попадание — действуем и показываем текст; несколько —
перечисляем и просим уточнить; ничего — так и говорим. Уточняющего
диалога с состоянием нет (потребовал бы pending-состояния канала, как у
вложений), человек повторяет команду точнее: для действий, половина
которых необратима, переспросить безопаснее, чем угадать.

Забытое исчезает и из Markdown-зеркала — §14.11 требует исключать
зеркало для DISABLED/DELETED, иначе Obsidian и Graphify продолжали бы
показывать то, что человек убрал. При возврате зеркало создаётся заново.

«Исправь» правит запись на месте, а не заводит новую: иначе исправление
незаметно превращалось бы в «запомни ещё раз», и старая версия
продолжала бы находиться поиском. Если правка даёт текст, который в
памяти уже есть, — отказ с указанием существующей записи.

Fail-closed в Telegram: при недоступности Control Plane плагин отвечает
«Ничего не изменил» и НЕ пропускает сообщение к модели. Половина команд
необратима, и «модель подтвердила, а ничего не произошло» здесь хуже
явной ошибки.

**Evidence §14.15 выдача оригинала документа (30.08.2026)**:
`helm_core/knowledge/documents.py` + `GET /api/panel/v1/knowledge/sources`
и `POST .../sources/{id}/download`. Закрывает пункт приёмки владельца
«проверяй принадлежность на каждом source, memory и download», который
до этого захода стоял как «неприменимо: скачивания нет вовсе».

Ключевое слово спеки — **original bytes**. Не восстановленный текст, не
разобранный Markdown, а ровно тот файл, который прислали, с тем же
SHA256. Поэтому в модуле нет ни парсера, ни модели: восстанавливать
нечем и не из чего, байты можно только отдать. Контрольная сумма
сверяется при каждой выдаче, и расхождение — отказ, а не «немного не
то»: разошедшийся файл означает потерю доказуемости происхождения
(§14.1 RAW immutable).

Источник, заведённый из готового текста (`ingest_text()`), файла на
диск не пишет вовсе — у него оригинала физически нет. Честнее сказать
это, чем отдать разобранный текст под видом оригинала; отдельный
понятный отказ.

Чужой документ отвечает «не найден», а не «запрещено»: существование
чужого файла — тоже сведения о нём.

**Скачивание сделано POST'ом, а не ссылкой**, по двум причинам сразу:
§14.15 требует, чтобы чувствительная выдача подчинялась
passkey-правилам, а свежее подтверждение приходит заголовком, которого
у обычной ссылки нет; и правило раздела «GET не запускает LLM» проще
держать, когда GET'ы остаются чистым чтением. Passkey требуется на
ЛЮБОЙ оригинал, не только на клиентский: спека называет отдельно
чувствительные, но выдача исходного файла и так поступок, а не
просмотр, и одно правило без исключений надёжнее двух с оговоркой.

§14.15 «disabled/archived/superseded можно скачать владельцу для
разбора, но нельзя использовать в обычных ответах» — здесь разрешено
именно то, что запрещено в `probe()`; заархивированное приходит с
пометкой `X-Helm-Review-Only`. Отдельного статуса «удалён» у источника
в схеме нет вовсе (строки исчезают только вместе с аккаунтом), поэтому
«удалённое недоступно» выполняется тем, что искать уже нечего — названо
в коде прямо, чтобы следующий читатель не искал несуществующий статус.

## Осознанно упрощено против буквы спеки

- `primary_domain_id`/per-user `knowledge_domains`/`knowledge_topics` —
  НЕ строится (то же решение, что в `V3.7-DELTA.md`: реестра доменов
  нет и не вводится этим заходом). `KnowledgeMemory.domain` — `str`
  через существующий `KnowledgeDomain` enum, как везде в кодовой базе,
  nullable — не блокирует запись при отсутствии совпадения.
- Векторный/embedding слой Micro-Memory ("direct FTS/vector unit") —
  только FTS (`tsvector`, тот же паттерн, что `KnowledgeChunk`).
  pgvector/embeddings (P8.5.4 остаток) не реализованы ни для
  документов, ни для памяти — не новый пробел, уже задокументированный.
- Ollama structured classifier для неоднозначных `Запомни`-команд — не
  реализован (Ollama вообще не установлен, P8.5.6 remains design-only,
  `docs/KNOWLEDGE_MODELS.md`). Классификация — детерминированные
  префиксы/regex (`Запомни`/`/remember`/`Сохрани в память`/`Не забудь`),
  без LLM вообще; неоднозначные случаи получают короткий уточняющий
  вопрос, не угадывание.
- Cross-user physical dedup намеренно НЕ реализуется — спека сама явно
  говорит "intentionally not implemented in v1", совпадает с нашим
  подходом без доп. усилий.
- Инвайт создаётся HMAC-подписанным internal API-вызовом, не формой в
  Panel (P8.6.5 не начат) — сама спека допускает этот промежуточный шаг
  ("activation remains owner-interactive pending").
- Файлы/ZIP/голос для KNOWLEDGE_USER через Dedicated Bot — НЕ
  реализованы (см. ADR-029: нужен отдельный raw-HTTP Telegram file-
  download, которого этот вебхук сегодня не делает); вложение получает
  явный "пока не поддерживается" ответ, не тихо игнорируется.
