# V3.7-DELTA — переход с v3.4 на v3.7 (только ZIP batch ingest)

Составлено по прямому распоряжению владельца 30.08.2026: «Продолжай
текущую реализацию, не переделывая working single-document pipeline.
Прими v3.7 как новый source of truth и реализуй ZIP исключительно как
durable batch/container layer перед существующим child-ingest
pipeline. P8.5 не считать PASS до прохождения ZIP acceptance tests из
v3.7.» Тот же принцип §31.0.1, что уже применялся в `V3.4-DELTA.md`: не
перезапускать рабочий пайплайн, зафиксировать только разницу, взять из
новой спеки ровно столько, сколько попросил владелец — не весь объём
документа.

## Чекпоинт перед изменениями (CONTINUE §1)

- 215/215 тестов control-plane зелёных на момент начала (после
  перезапуска упавшей песочницы Postgres — тот же класс проблемы среды,
  что уже случался в этой сессии, не связан с кодом).
- Текущий single-document ingest (P8.5.1/2/7) живьём подтверждён —
  MAX и Telegram, оба канала, все три шага диалога, включая дедуп
  повторной отправки (см. `docs/KNOWLEDGE_INGEST.md`).
- DB backup/restore — не выполнялся отдельно этим заходом до схемы
  (сервер эфемерный dev-sandbox, не прод; на реальном VPS перед
  накаткой миграции — тот же `scripts/backup.sh`+`restore_test.sh`,
  что уже используется, ничего нового не требуется).

## Что v3.7 вводит целиком (для справки, НЕ реализуется этим заходом)

Полная спека v3.7 (`HELM_FINAL_v3.7_2026-08-30.md`, 7260 строк) — это
P8.5.1 (реестр доменов `knowledge_domains`, authority/versioning
источников) через P8.5.11 (кэш/инвалидация). ZIP batch ingest —
подраздел **P8.5.2.1**, один из одиннадцати. Остальные десять НЕ
затрагиваются этим заходом:

- P8.5.1 domain registry (`knowledge_domains`/`knowledge_topics`) —
  наша `KnowledgeDomain` остаётся закрытым Python-enum, не таблицей.
- P8.5.3 парсеры (уже частично сделано, GigaAM отдельно).
- P8.5.4 индексация (embeddings/pgvector/rank fusion) — не начато.
- P8.5.5 Graphify — не начато; в ZIP-агрегации это означает, что
  graph-статус любого child всегда `NOT_APPLICABLE` (см. ниже).
- P8.5.6 Ollama Knowledge Localizer — задокументирован дизайн
  (`docs/KNOWLEDGE_MODELS.md`), не реализован.
- P8.5.7 zero-paid router, P8.5.8 original-file return, P8.5.9/10
  Panel/bot management, P8.5.11 cache — не начаты.

## Диапазон изменений этого захода (P8.5.2.1 из v3.7, §14.4.0/14.5.1-2/14.6/14.7.6-7)

Взято из v3.7 **буквально**:

1. `knowledge_ingest_batches` + `knowledge_batch_items` — схема БД.
2. Безопасная потоковая распаковка ZIP (§14.7.6) — весь список проверок
   (traversal/symlink/encrypted/nested/bomb/CRC/MIME).
3. Домен архива спрашивается один раз, наследуется всем детям (§14.5.1).
4. Агрегация статусов batch, ровно одно финальное уведомление с
   `completion_revision` в dedup-ключе (§14.5.2).
5. `retry_failed` / `cancel_remaining` / `disable_created_sources`.
6. Очередь без взрыва воркеров — переиспользуется существующий
   единственный `helm-knowledge-worker`, не N воркеров на N файлов
   (§14.7.7 — у нас и так один воркер-процесс, требование выполняется
   тривиально самой текущей архитектурой, не нужен отдельный лимитер).
7. 11 acceptance-тестов из CONTINUE §10.

Осознанно **адаптировано** под уже существующую, более простую модель
данных (не переделывается — используется как есть):

- `domain` — `str` через `KnowledgeDomain` enum (как везде в текущем
  коде), НЕ `primary_domain_id` FK на несуществующий `knowledge_domains`.
- Дедуп member — существующий `register_file_for_ingest()` (глобальный
  SHA256 по сырым байтам, уже реализован и покрыт тестами) — это
  ЕСТЬ D0 из §14.6, ничего нового писать не нужно. Item-статус
  `EXACT_DUPLICATE` ставится, когда `register_file_for_ingest()`
  возвращает `created=False`.
- Итоговый `sensitivity` архива — та же логика, что уже есть в
  `chat_intake.py` (`simpas/zapiski` → принудительно
  `client_restricted`), не вводится отдельное понятие `security_scope`.
- Graph-статус любого item — всегда `NOT_APPLICABLE` (Graphify не
  реализован), финализация batch не ждёт несуществующей стадии.

Осознанно **не реализовано** (не часть ZIP-слоя, отдельные, не
запрошенные задачи из более широкой v3.7):

- `domain_mismatch_candidate` — требует классификатор контента,
  которого нет; не строится.
- `NORMALIZED_DUPLICATE`/D2 near-duplicate (`normalized_text_sha256`,
  `POSSIBLE_NEW_VERSION`) — требует §14.6 D1/D2, отдельная, более
  крупная задача дедупа за пределами ZIP; item может быть только
  `READY`/`EXACT_DUPLICATE` по бинарному SHA256, как и одиночные файлы
  сегодня.
- Panel-вкладка «Архивы» (`GET /api/panel/v1/knowledge/batches`) — нет
  в списке из 11 acceptance-тестов CONTINUE §10; тот же принцип, что
  P8.5.8 Panel Knowledge management раньше в этой сессии (владелец
  выбрал Panel как основной интерфейс, но это отдельная задача,
  которая появится после того, как заработает сам batch-пайплайн).
- `knowledge_batch_final:<batch_id>:<completion_revision>` — реализовано
  дословно как в спеке (существующий `outbox.enqueue()` уже поддерживает
  произвольный `reference`, менять `outbox.py` не пришлось).

## Already satisfied

Инфраструктура, на которой строится ZIP-слой, уже на месте:

- `outbox`/`dispatch.py` (§10.3) — доставка финального уведомления идёт
  тем же путём, что уже доставляет уведомления P8.5.7 (включая свежий
  `TelegramSender`).
- `register_file_for_ingest()`/`worker.py::process_job()` — весь child
  pipeline (SHA256, парсинг, чанки, frontmatter, уведомление) уже
  реализован и живьём подтверждён; batch-слой его вызывает, не дублирует.
- `chat_intake.py` — паттерн «спросить домен один раз, ждать следующего
  сообщения того же канала» уже существует для одиночных вложений;
  batch переиспользует ту же механику диалога, только с другим типом
  pending-записи.
