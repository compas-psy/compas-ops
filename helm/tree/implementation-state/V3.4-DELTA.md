# V3.4-DELTA — переход с HELM v3.3 на v3.4

Составлено по требованию §31.0.1 ТЗ v3.4: не перезапускать deployment,
не переустанавливать работающие A/B-сервисы, сравнить `STATUS.json` и
фактически работающий VPS со спекой, зафиксировать только разницу.

**Путь.** §31.0.1 называет `/opt/helm-state/implementation/V3.4-DELTA.md`
— пути `/opt/helm-state/` на этом сервере не существует; вся эта серия
документов (`STATUS.json`, `WORKPLAN.md`) с самого начала живёт в git,
не на VPS runtime (`helm/tree/implementation-state/`). Этот файл кладётся
туда же, ради единообразия, а не по названному в спеке пути.

## Диапазон изменений v3.3 → v3.4

Проверено построчным diff обеих версий (`diff HELM_FINAL_v3.3
HELM_FINAL_v3.4`), не только по оглавлению — различий за пределами
перечисленного ниже нет:

1. §14 переписан целиком: `Memory и RAG` (5 коротких подпунктов) →
   `HELM Knowledge / Memory / RAG — «второй мозг»` (19 подпунктов,
   §14.0–§14.18) — новая подсистема.
2. §9.3 (Telegram gate) и §10.2 (MAX): добавлен шаг **Knowledge Probe**
   перед диспетчеризацией к Hermes — `LOCAL_ANSWER` пропускает Hermes
   целиком, `NEEDS_REASONING` прикладывает evidence pack.
3. §26.1 (backup): HELM Knowledge RAW/Vault/индексы добавлены в scope;
   веса embedding/local-LLM/GigaAM и derived-вывод Graphify — исключены
   (re-downloadable/reproducible, как уже исключены веса других моделей).
4. §30.8: одна строка про исключение `/opt/helm-knowledge` из
   Forgejo/GitHub remotes.
5. §30.8.5 — новый раздел тестов HELM Knowledge.
6. §31.0.1 и фаза **P8.5** — процессные разделы про сам переход.

Ничего в approval architecture, LiteLLM routing, Forgejo/GitHub
архитектуре, навигации Panel, SignalAI-протоколе не менялось — это
явно подтверждено и текстом §31.0.1, и построчным diff.

## Already satisfied

Ничего из §14 v3.4 не было реализовано ранее — подсистема целиком новая.
Инфраструктура, на которой она строится, уже на месте и трогать не
нужно:

- PostgreSQL (§14.9 требует «уже существующий PostgreSQL + pgvector») —
  сервер поднят; расширение `pgvector` в кластере ещё не проверено
  (см. «needs additive change»).
- Backup/restic pipeline (`scripts/backup.sh`) — уже параметризован
  списком путей, добавление `/opt/helm-knowledge` не требует новой
  инфраструктуры, только строки в список (см. ниже).
- `helm-control` (Hermes-плагин) и `/hooks/max` (Control Plane) — точки
  вставки Knowledge Probe уже существуют и работают (P7 MAX подтверждён
  живьём 29.08.2026) — новый шаг встраивается в уже рабочий путь, не
  создаёт его заново.
- Namespace-мышление (домены/sensitivity) уже присутствует в кодовой
  базе как паттерн (`domain: String` на `Task`, `Decision`,
  `sensitivity: String` на `Artifact`) — новые таблицы следуют тому же
  стилю, не изобретают новый.

## Needs additive change

Реализуется в этом заходе (P8.5.1, частично P8.5.4/5 — только лексика,
без embeddings) и следующих:

- **Схема БД**: 6 новых таблиц из §14.4 (`knowledge_sources`,
  `knowledge_chunks`, `knowledge_notes`, `knowledge_relations`,
  `knowledge_ingest_jobs`, `knowledge_answer_runs`) — alembic-миграция
  поверх существующей `f12e419c664b_initial_schema`.
- **Каталоги** `/opt/helm-knowledge/*` (§14.2) — не коммитятся, не
  зеркалятся, создаются на сервере отдельным шагом деплоя.
- **Free-first Knowledge Probe** (§14.11) как HTTP-эндпоинт Control
  Plane, вызываемый из `helm-control`/`hooks.py` ДО обращения к Hermes.
- **Z0/Z1 answer modes** (§14.12) — детерминированные, без LLM.
- **Backup scope** — добавить `/opt/helm-knowledge` (кроме `derived/`)
  в `scripts/backup.sh`.

Отложено на следующий заход (требует установки моделей/пакетов и
бенчмарка на живом 12GB VPS — не делается офлайн, спека сама явно
требует «P8.5 benchmark выбирает модель ... не hardcode»):

- Парсеры (MarkItDown/Docling/ffmpeg) и реальный ingest-pipeline
  (P8.5.2).
- GigaAM ASR (P8.5.3).
- Dense retrieval — выбор embedding-модели, pgvector-индекс (P8.5.4,
  вторая половина).
- Z2 (опциональный локальный генератор) — по спеке сам необязателен и
  не блокирует остальное (§14.12: «Z2 is not allowed to delay B.5
  completion»).
- Graphify A/B-бенчмарк (P8.5.6).
- Реальный Telegram/MAX attachment-ingest (протокол spool/RAW,
  P8.5.7) — probe/gate встраивается в этом заходе, но без чего
  принимать вложения ещё нечего.
- Строка `Knowledge` в Panel «Система → Интеграции» (P8.5.8) —
  бессмысленна, пока нет данных, которые она показывает.

## Conflicts found

Один: §14.15 требует для `health` «separate schema/user» — этот заход
даёт только логическое разделение (колонка `domain`), НЕ отдельную
схему/роль Postgres. Это сознательное упрощение первого прохода, не
случайный пропуск — фиксируется здесь явно, чтобы не выдать частичное
решение за полное. Отдельная схема/роль для health — самостоятельная
задача, не блокирует остальной P8.5.

Второе: §14.9 явно требует pgvector, но выбор embedding-модели (P8.5.4)
отложен — поэтому extension пока не создаётся и колонка
`knowledge_chunks.embedding` не добавляется в этой миграции: pgvector
требует фиксированной размерности при создании колонки (1024 у BGE-M3
против 768 у e5-base), а спека прямо запрещает хардкодить выбор до
бенчмарка. Добавление колонки — отдельная миграция после решения.

подсистема, не модификация существующей). Новые тесты — по §30.8.5,

парсеров/ASR — тесты на них появятся вместе с P8.5.2/3.
