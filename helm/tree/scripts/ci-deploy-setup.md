# Как дать агенту работать на живом сервере

Три действия владельца, дальше агент выкатывает и проверяет сам.

Механизм — GitHub Actions, и это не обходной путь: устав (CLAUDE.md
§5.4) прямо требует, чтобы секреты жили только в GitHub Secrets. Ключ
кладётся туда, workflow им пользуется, агент запускает workflow и читает
логи — но самого ключа не видит никогда.

## 1. Завести отдельный ключ для CI

На своей машине:

```powershell
ssh-keygen -t ed25519 -f "$env:USERPROFILE\.ssh\helm_ci_key" -C "github-actions" -N '""'
```

**Отдельный от вашего `helm_deploy_key`, не тот же самый.** Смысл: если
понадобится отозвать доступ CI, вы удаляете одну строку и не теряете
собственный вход на сервер.

Положить публичную часть на сервер:

```powershell
type "$env:USERPROFILE\.ssh\helm_ci_key.pub" | ssh -i "$env:USERPROFILE\.ssh\helm_deploy_key" helm@185.250.44.137 "cat >> ~/.ssh/authorized_keys"
```

## 2. Добавить два секрета в GitHub

`compas-psy/compas-ops` → Settings → Secrets and variables → Actions →
New repository secret.

| Имя | Что вставить |
|---|---|
| `VPS_SSH_KEY` | **приватный** ключ целиком: содержимое `helm_ci_key` |
| `VPS_KNOWN_HOSTS` | вывод `ssh-keyscan 185.250.44.137` |

```powershell
ssh-keyscan 185.250.44.137
```

**Это два РАЗНЫХ ключа, и их легко перепутать.** Ваш ключ — то, чем вы
представляетесь серверу. `known_hosts` — ключи самого сервера, то, чем
он представляется вам, чтобы под него нельзя было подделаться.
Комментарий `github-actions`, который вы задали при генерации, живёт
только в вашем **публичном** ключе и в `known_hosts` не встречается.

Как отличить, что куда:

| Файл | Куда идёт | Начинается | Заканчивается |
|---|---|---|---|
| `helm_ci_key` | секрет `VPS_SSH_KEY` | `-----BEGIN OPENSSH PRIVATE KEY-----` | `-----END OPENSSH PRIVATE KEY-----` |
| `helm_ci_key.pub` | `authorized_keys` на сервере (шаг 1) | `ssh-ed25519 AAAAC3…` | `github-actions` |
| вывод `ssh-keyscan` | секрет `VPS_KNOWN_HOSTS` | `185.250.44.137 ssh-ed25519 AAAA…` | ничем особенным |

`ssh-keyscan` выдаёт несколько строк — по одной на каждый тип ключа
сервера. Вставляйте все. Строки, начинающиеся с `#`, если попадут при
копировании из консоли, безвредны: `known_hosts` считает их
комментариями.

Можно добавить `-H` — тогда адрес хоста будет захэширован. На
безопасность одного хоста в CI это не влияет, а отлаживать сложнее:
глазами не видно, к какому серверу относится строка. Поэтому здесь без
хэширования.

Зачем этот секрет вообще: без него пришлось бы отключить проверку хоста
(`StrictHostKeyChecking=no`), а это ровно та дыра, ради которой
`known_hosts` и существует — подменивший себя сервер получил бы ваш
доступ молча.

## 3. Сказать агенту

После этого достаточно написать: «выкатывай». Агент сам запустит
workflow нужным действием и прочитает логи.

---

## Что агент сможет запускать

`.github/workflows/deploy.yml`, действие выбирается при запуске:

| Действие | Что делает |
|---|---|
| `verify` | Только смотрит: контейнеры, ревизия схемы, роль базы, объём знаний, место, дата бэкапа. **По умолчанию** — случайный запуск ничего не меняет |
| `backup` | Снимает точку возврата |
| `deploy` | Точка возврата → сборка панели → доставка кода, конфигурации и панели → пересборка ядра и воркера → перезапуск Caddy и Hermes |
| `migrate` | `alembic upgrade head` с показом «было/стало» и проверкой, что записей без владельца ноль |
| `restore-test` | Бэкап и проверка восстановления, включая проверку тенантности |
| `rollback` | Откат схемы до указанной ревизии |

Итог каждого запуска приходит вам в Telegram (используются уже
заведённые `TG_BOT_TOKEN`/`TG_CHAT_ID`).

## Границы, которые остаются за вами

Workflow сознательно **не** умеет:

- заводить секреты на сервере — токен Knowledge-бота вы кладёте руками
  (§6 устава: агент не создаёт и не пересылает токены);
- удалять данные и делать необратимое — только выкат кода и схемы;
- выкатывать без вашего запуска — нет ни расписания, ни триггера на push.

## Если не хотите держать 22-й порт открытым наружу

Альтернатива — self-hosted runner прямо на сервере: он сам ходит на
GitHub исходящим соединением, входящий SSH становится не нужен, и порт
можно закрыть совсем. Настройки чуть больше (служба на сервере), поэтому
как первый шаг предлагается обычный вариант; переход на self-hosted
позже ничего не ломает — меняется одна строка `runs-on`.

## Проверка, что всё сошлось

Первым запуском стоит сделать `verify`: он ничего не меняет, но покажет
и что ключ работает, и текущее состояние сервера. Отдельно он проверяет,
что роль базы **не суперпользователь** — суперпользователь молча обходит
изоляцию между пользователями, и второй слой защиты превратился бы в
декорацию незаметно.
