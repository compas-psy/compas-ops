# HELM Panel — бриф для Claude Design

**Что это:** пульт контроля личной AI-системы HELM. Один пользователь — владелец. Режим: *Operate* (человек выполняет задачу, интерфейс должен исчезнуть).
**Где живёт:** `helm.cmpas.ru/`, за аутентификацией.
**Не является:** чатом с ассистентом, редактором skills/промптов, заменой n8n UI, «AI-дашбордом».

---

## 1. Кто и когда

Владелец открывает панель **с телефона, между делами, каждый день как ритуал** (утро/вечер, 1–3 минуты) и дополнительно по алерту. Состояние: занят, хочет за 10 секунд понять «всё ли в порядке и что от меня нужно», при необходимости — провалиться в деталь. Ноутбук — вторичный сценарий (разбор инцидента, недельный обзор).

Следствия:
- первый экран должен быть прочитан целиком без скролла на телефоне
- одобрения — самая частая *активная* задача; они делаются и в Telegram, и здесь, поэтому панель обязана показать больше, чем помещается в Telegram-сообщение (полный текст, diff, preconditions)
- ноутбук получает ту же информацию в более плотной раскладке, не другой интерфейс

## 2. Что должно быть правдой (и чего не должно быть)

Панель показывает **факты из базы**, не мнения. Каждое число имеет единицу, базу сравнения и источник. Ничего не «генерируется» на лету для красоты.

### Запрещено (AI-шум)

- приветствия, «доброе утро, Илья», мотивационные фразы
- LLM-сгенерированные резюме, «AI insights», «рекомендации» на экранах панели — единственный текст от модели, который допустим: сохранённая одна строка «почему вызвана дорогая модель» и сохранённое короткое описание задачи
- декоративные иконки при каждом числе, эмодзи, иллюстрации пустых состояний
- KPI-карточки с большими цифрами без порога/базы сравнения
- круговые индикаторы, gauge-спидометры, прогресс-кольца
- sparkline «для оживления»: график только там, где вопрос — тренд (диск, расход), и только при ≥7 точках
- конфетти, анимации появления, skeleton-«танцы», орchestrated page load
- карточки внутри карточек; тени и рамки без функции
- чат-виджет, «спросить ассистента»
- «показать ещё» с бесконечным скроллом на первом экране
- проценты без абсолюта (не «RAM 71%», а «RAM 8,5 / 12 GB · порог 9 GB»)

### Обязательно

- один primary action на экран
- у каждого элемента, требующего внимания, — причина и следующее действие в той же строке
- временные метки: относительные («12 мин назад») с абсолютным временем по тапу/hover
- id/хэши/SHA — моноширинным, копируются одним тапом
- пустые состояния — факт, а не утешение: «Нет ожидающих одобрений»
- ошибка загрузки блока — показывается внутри блока, остальной экран работает

## 3. Структура: 5 разделов

Восемь разделов из обсуждения схлопнуты до пяти, потому что на телефоне это предел навигации без «ещё», а «Интеграции», «Рутины/политики» и «Журнал» — это редкие сценарии одного типа: «залезть в систему».

### 3.1. Сегодня (стартовый экран)

Одно вертикальное полотно, читается без скролла на 390×844.

Порядок сверху вниз — по срочности:

1. **Строка состояния**: одно слово (`В порядке` / `Внимание` / `Проблема`) + если не «в порядке» — одна строка с причиной и ссылкой в раздел. Не светофор-кружок, а текст с цветом фона строки.
2. **Ждут тебя**: N одобрений. Показаны первые 3 в компактном виде (тип действия · одна строка сути · срок) с кнопками *Одобрить / Отклонить* прямо здесь для простых и *Открыть* для тех, где нужен diff/текст. Если 0 — одна строка «Нет ожидающих одобрений», блок не исчезает (постоянство раскладки важнее экономии места).
3. **Деньги сегодня**: `$2,40 из $10 · вчера $3,10`. Одна строка. Если есть вызов дороже standard — вторая строка: модель · задача · «почему».
4. **Задачи**: `3 в работе · 1 застряла` — застрявшая с названием и временем без heartbeat. Тап → раздел Задачи с фильтром.
5. **Сервер**: три строки, только то, что имеет порог: `Диск 41 / 100 GB · +0,3 GB/день · 90% через 190 дн.`, `RAM 7,1 / 12 GB`, `Бэкап 6 ч назад · restore-тест 3 дн.` Цвет строки — только при WARN/CRITICAL.
6. **Ночью сделано**: 3–5 строк завершённых задач с 22:00 до сейчас (название · стоимость). Это ответ на «что HELM сделал, пока я спал», без LLM-пересказа.

Обновление: данные грузятся блоками; устаревший блок показывает возраст данных, не спиннер.

### 3.2. Одобрения

Две вкладки: **Ожидают** (default) · **История**.

Карточка ожидания (одна на экран в раскрытом виде):
- тип действия (человеческое название + техническое имя моноширинным)
- задача-источник (ссылка)
- **суть действия в его родной форме**: для публикации — полный текст поста как он будет отправлен + канал; для merge — список файлов и diff-статистика, кнопка «diff»; для трат — сумма, получатель, назначение; для деплоя — SHA и что изменится
- **preconditions**: список с фактическим статусом каждого (`CI зелёный на a1b2c3d ✓`, `цена не менялась ✓`) — это единственный «чеклист» в панели, и он не декоративный
- хэш действия моноширинным (усечённый, копируется)
- срок: «истекает через 18 ч»
- уровень доверия для этого типа: «7 из 10 supervised» — маленькая строка, без прогресс-бара
- кнопки: **Одобрить** (primary) · Отклонить (secondary, с необязательным полем причины) · при отклонении — ничего не спрашивать дважды

Одобрение требует подтверждения passkey. Ответ — одна строка «Выполнено · 14:02 · результат» на той же карточке, без перехода.

Пакет: если ожидают >3 однотипных некритичных — кнопка «Одобрить все N» с явным списком того, что войдёт; каждое подписывается отдельно.

История: список строк: дата · тип · решение · кто (Telegram/панель) · результат. Фильтр по типу. Без графиков.

Подраздел **Доверие** (внизу вкладки История): таблица `тип действия · уровень · supervised N/10 · последний инцидент`. Предложение системы понизить уровень появляется как обычное одобрение в очереди, а не как баннер.

### 3.3. Задачи

Список, сгруппированный по состоянию: **Застряли · В работе · Ждут одобрения · Готово (сегодня)**. Строка: название · домен · профиль · время в состоянии · стоимость.

Карточка задачи:
- шапка: название, статус, домен/риск, стоимость, длительность
- **таймлайн** `task_events`: вертикальный список «время · актор · событие». Не «активность» с аватарами, а лог.
- какие skills/модели были задействованы (одна строка на вызов: alias → модель · токены · $)
- артефакты (ссылки, sha)
- действия: *Повторить* (YELLOW), *Остановить*, *Открыть в Kanban Hermes* (ссылка на 127.0.0.1 работает только через tunnel — показывать с пометкой)

Поиск по названию/id. Фильтр по домену. Ничего больше.

### 3.4. Деньги

Три блока, один экран:

1. **Сегодня / лимит** + **месяц / soft-alert** — две строки с цифрами. Kill switch: строка состояния `Kill switch: выкл` с кнопкой изменения (RED-действие → уходит в Одобрения, здесь не срабатывает напрямую).
2. **Расход за 30 дней**: один столбчатый график по дням, тап на столбец → раскладка по профилю. Второй график не нужен; переключатель «по профилю / по alias / по модели» меняет разбивку того же графика.
3. **Дорогие вызовы**: таблица последних вызовов дороже `helm-standard`: время · задача · alias → модель · $ · «почему» (сохранённая строка). Это ответ на «почему был вызван Opus».

Подраздел **Модели** (вкладка): текущая матрица `alias · primary модель · challenger · последний eval (дата, результат)`. Auto-demotion события — как строки лога. Изменение лимитов — форма, отправляющая RED-действие.

### 3.5. Система

Единственный раздел с внутренней навигацией (вкладки): **Сервер · Интеграции · Рутины · Политики · Журнал**.

**Сервер**: таблица ресурсов `имя · сейчас · порог WARN/CRIT · прогноз до порога` (диск, inodes, RAM, swap, Docker disk, BuildKit cache). Один график — диск за 30 дней с линией порога. Список контейнеров: имя · состояние · рестарты за 24 ч · память. Строки бэкапа: последний, размер, restore-тест, TLS до. Лог автоочистки (последние 20 строк). Кнопки: *Запустить restore-тест* (YELLOW), *Снапшот Kanban* (YELLOW).

**Интеграции**: список `сервис · состояние · последняя проверка · деталь`: Telegram, MAX (+ размер outbox), LiteLLM, OpenRouter, каждый MCP, n8n (4 workflow по строке: активен · последний запуск · дата экспорта · ссылка в n8n UI), git-зеркало (свежесть по репо). Никаких схем-диаграмм связей.

**Рутины**: таблица `имя · расписание · вкл · последний запуск · результат · $` · кнопка *Запустить сейчас*. Тумблер вкл/выкл — YELLOW.

**Политики**: таблица actions.yaml как есть (`действие · уровень · hard`). Очередь skills-candidates: `skill · что изменилось · material?` → *Открыть diff* · *Promote* (уходит в одобрения). Список ADR — ссылки на файлы.

**Журнал**: одна таблица `время · актор · событие · задача`, фильтры: тип события, «только security», период. Security-события выделены строкой цвета. Экспорт — CSV.

## 4. Навигация и раскладка

- Телефон: нижняя панель, 5 пунктов, счётчик ожидающих одобрений на «Одобрения». Заголовок раздела сверху, без hamburger.
- Ноутбук: левая узкая колонка с теми же 5 пунктами; контент одноколоночный до 1100 px, на «Система» — вкладки горизонтально. Таблицы получают больше колонок, не другой интерфейс.
- Глубина ≤ 2: раздел → карточка. Модальные окна — только для подтверждения passkey и diff.

## 5. Визуальная система (намеренно сдержанная)

- Один шрифт: системный sans (`-apple-system, Inter` fallback). Моноширинный для id/хэшей/SHA/сумм в таблицах.
- 4 размера, 2 веса. Никаких display-заголовков.
- Цвет: нейтральная шкала + один accent для primary action и текущего выбора + 3 семантических (warn / critical / ok). Ok — почти невидимый; внимание должно уходить на warn/critical. Нет градиентов, нет цветных фонов карточек.
- Тёмная/светлая по системной настройке, без переключателя в UI.
- Плотность: строки 40–44 px на телефоне, таблицы могут быть плотнее на ноутбуке.
- Движение: только изменение состояния (кнопка → «Выполнено»), 150–200 ms. Ничего при загрузке страницы.
- Loading: блок показывает последнее известное значение с пометкой возраста; при первом заходе — серые плейсхолдеры формы строк, без анимации.

## 6. Состояния, которые нужно спроектировать

- всё в порядке, 0 одобрений (самый частый экран — он не должен выглядеть «пустым», он должен выглядеть «спокойным»)
- 1 критический алерт + 5 одобрений (утро понедельника)
- Control Plane недоступен: панель показывает последний snapshot с явным «данные от 07:12, сервер не отвечает» и ссылку на Guardian-статус (Guardian отдаёт статический JSON независимо)
- одобрение истекло / хэш не совпал / precondition упал в момент исполнения — сообщение на карточке, не тост
- kill switch сработал
- вход: Telegram Login → passkey; неудачный вход

## 7. Аутентификация и безопасность (не спроектировать нельзя)

- вход: Telegram Login widget, проверка owner id, затем passkey (WebAuthn) — обязательный второй фактор
- любое действие-запись — повторный passkey (step-up), без «запомнить на 30 дней»
- сессия 24 ч, один активный device по умолчанию
- панель никогда не показывает: сырые промпты, raw health-данные, значения секретов, содержимое клиентских заметок
- все записи — через те же actions Control Plane; панель не имеет собственных прав

## 8. Что оставить Claude Design

Композиция первого экрана и карточки одобрения — это 80% ценности. Начать с них в мобильной раскладке, затем Деньги и Задачи, «Система» — как список таблиц по спецификации выше. Ноутбучная версия — после мобильной, как расширение плотности.

Открытые решения, которые дизайн не должен придумывать сам: формулировки человеческих названий действий (берутся из `actions.yaml` с полем `title_ru`), состав preconditions (из registry), цвет accent (любой сдержанный; не Telegram-синий, чтобы не путать с кнопками мессенджера).
